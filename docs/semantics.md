# wmfs 语义承诺（对外文档）

> 状态：**accepted（人类于 2026-10-20 批准）**。本文是理念文档 10.3 要求的对外承诺：一致性模型、POSIX 放松清单、配额精度、隔离承诺、首发不支持的东西。权威设计见 [design.md](design.md)（3.1、3.9、6.3 等节）；本文与 design.md 冲突时以 design.md 为准并修正本文。
> 原则 7"诚实的语义"：做不到的不承诺；宁可拒绝操作，也不静默丢数据、静默降级或静默忽略策略。

---

## 1. 怎么查询你得到的语义

- `wmfs get <路径>`：列出该目录的生效属性及来源，最后一行固定是 `semantics:`，例如
  `semantics: consistency=cto attr_ttl=1s (来源 /); quota=quantum:64MiB overshoot<=64MiB*writers (来源 /home/alice); durability=replicas:声明3/实际1 fsync:all-replicas; isolation=shared-device(份额,不承诺尾延迟)`
  "实际"是这个目录下的新文件此刻能得到的副本数；声明与实际不同时，这一行之前还会多打印一行警告。
- `wmfs status <路径>`：第一行是集群警告（例如"有 3 条链少于声明副本数""故障域重叠"）；之后逐个属性列出声明、来源、实际与是否一致（例如 replicas 声明 3、实际 2 的文件数；配额用量与软限计时；QoS 保底欠额；审计消费者落后多少条），以及隔离承诺、后台迁移进度。
- `GET /api/v1/semantics`：本文要点与当前集群参数（租约时长、cap 有效期）。

## 2. 一致性模型

一致性等级是目录属性 `consistency`，取值 `cto`（默认，可带子键 `attr_ttl`，例如 `consistency=cto,attr_ttl=3s`）或 `strong`，对**之后新打开**的文件生效。

### 2.1 元数据（两种等级相同）

所有元数据操作（创建、删除、rename、属性、锁……）在元数据 leader 上**线性一致**：修改在多数派落盘并应用后才返回；读取先确认 leader 身份再读。rename 对所有观察者原子：要么旧名存在、要么新名存在。

### 2.2 `cto`（close-to-open，默认）

1. 写者 `close()` 成功返回后，**之后**在任何节点发起的 `open()` 一定看到该文件此前写入的全部数据、新长度与 mtime。
2. 文件打开期间，不保证看到其他节点的新写入；但每次读到的每个 chunk 都是某个已提交的版本，不会读到"写了一半"的数据，也不会"先读到新、后读到旧"。
3. 其他节点的创建、删除、rename、属性变化，最多 `attr_ttl`（目录属性，默认 1 s，范围 0–10 s；挂载参数 `--max-attr-ttl` 只能把它调得更小）后在本节点可见；`open()` 总会重新校验。
4. 本节点内：写后读总能读到自己的写。
5. 用 `O_DIRECT` 打开的文件，每次 `write()` 都同步写到所有副本并提交长度后才返回（与 strong 的写相同）。

### 2.3 `strong`

1. 客户端不缓存数据与属性（direct_io，属性 TTL 0）。
2. 每次 `read()` 先线性一致地取一次文件长度，再读数据；每次 `write()` 同步写到所有副本并同步提交长度后才返回。于是任意两个节点之间"写完立刻可读到"。单个 chunk（默认 4 MiB）内的读写线性一致；跨 chunk 的一次大写不是原子的（与本地文件系统相同，需要原子性请加锁）。
3. 跨节点 `O_APPEND`：每次追加的偏移由元数据服务原子分配，多个节点并发追加互不覆盖、按分配顺序排列。
4. 跨节点共享可写 `mmap`：**拒绝**——strong 文件上任何 `MAP_SHARED` 映射（即使只读）返回 `ENODEV`；`MAP_PRIVATE` 可用。【ADR-0013，偏离理念文档 8.2"仅在 strong 下支持"】
5. strong 目录里新建的文件不会内联到元数据库；已有的内联小文件在第一次以写方式打开时先转成普通存储（对应用透明）。
6. 代价：每次写一次元数据提交（本机约 3–6 ms）。适合日志、共享状态等"协调为主"的负载，不适合大量小块随机写。

### 2.4 锁是同步点（两种等级都成立）

`fcntl` 字节范围锁与 `flock` 是集群范围的，存在复制状态里，元数据 leader 切换不丢锁。拿到锁时客户端丢弃该文件的本地缓存；释放锁前先把写入提交出去。所以用锁协调的程序在 cto 下也正确（与 NFS 相同）。持锁客户端失联时，只有在它被驱逐、且所有数据节点都已拒绝它之后，锁才会转交给别人。阻塞等锁（`F_SETLKW`、阻塞的 `flock`）由客户端定期重试实现（50 ms 起，最长每 1 s 一次）：**不保证先来先得**，竞争激烈时某个等待者可能等很久；等锁的进程再多也不会卡住挂载点。

### 2.5 持久性

| 操作返回 | 意味着 |
|---|---|
| 元数据操作（create、rename、setattr……） | 已在元数据多数派落盘 |
| cto 的 `write()` | 数据在本客户端的写回缓冲里（尚未离开本机） |
| cto 的 `close()` | 数据已到达链上全部副本的内存（页缓存）并提交了长度：**可见，但不保证落盘** |
| `fsync()` / `fdatasync()` / `O_SYNC` 写 | 链上全部副本已 `fdatasync`，长度已在元数据多数派落盘 |
| strong 的 `write()`、cto 下 `O_DIRECT` 文件的 `write()` | 已到达全部副本的内存并提交了长度（落盘仍需 fsync） |

**所有副本同时掉电**时，未 fsync 的数据可能丢失——即使它曾被读到过（文件大小可能已更新，丢失区间读为 0）。这与本地文件系统的 POSIX 语义相同；"有 3 个副本"不等于"不需要 fsync"。fsync 过的数据在所有副本上都已落盘，不会因为掉电丢失。（真实设备上的掉电行为本机无法验证，见第 10 节。）

## 3. POSIX 支持与放松清单

### 3.1 支持

普通文件、目录、符号链接（目标 ≤ 4096 字节）、硬链接（仅文件，每个文件 ≤ 1000 个）、fifo/socket/设备节点（只存元数据）；名字 1–255 字节；`rename`（含 `RENAME_NOREPLACE`、`RENAME_EXCHANGE`）；`chmod/chown/utimensat/truncate`；`fallocate` 模式 0；xattr（`user.*`、`security.*`、`trusted.*` 仅 root、POSIX ACL；每个文件合计 ≤ 64 KiB）；POSIX ACL（父目录有默认 ACL 时新建对象不应用 umask，符合 POSIX）；`fcntl` 字节范围锁与 `flock`；`O_APPEND/O_EXCL/O_TRUNC/O_DIRECT/O_SYNC/O_DSYNC`；`fsync/fdatasync`；稀疏文件；跨客户端"删除后仍打开"（打开者关闭前仍可读写）；`statfs`；`readdir/readdirplus`。

### 3.2 理念文档 8.2 的放松（原文对应）

1. `atime` 按 relatime 语义更新。
2. 跨节点共享可写 `mmap`：首发**任何等级都不支持跨节点一致**；strong 下明确拒绝（`ENODEV`），cto 下只有同一节点内一致（ADR-0013）。
3. 不支持强制锁；字节范围锁与 flock 支持。
4. 跨节点 `O_APPEND` 的顺序仅在 `consistency=strong` 下保证；cto 下由各节点内核按自己缓存的长度计算偏移。
5. `cto` 模式下，另一节点的写入在本节点下一次 `open` 后可见。
6. 配额在客户端缓存写回前可能短暂超限，超限幅度有上界并可配置（第 5 节）。

### 3.3 本设计新增的放松（ADR-0014，需人类批准）

1. cto 下目录项与属性缓存最长 `attr_ttl`（目录属性，默认 1 s，受挂载参数 `--max-attr-ttl` 限制）陈旧。
2. `flock` 与 `fcntl` 锁共用一个锁空间（FUSE 库没有把"这是 flock"的标志传给文件系统）：同一进程对同一文件混用二者会互相冲突（Linux 本地文件系统上二者互不影响）。
3. 阻塞的 `F_SETLKW` 不能被有处理函数的普通信号打断；致命信号（`kill -9`，或没有处理函数的 SIGINT/SIGTERM）会在 1 秒内让等待结束、进程正常退出。
4. 不做死锁检测（不返回 `EDEADLK`）。
5. 通过 `mmap` 写入的数据，配额错误在写回阶段发生，于 `msync/fsync/close` 报告。
6. strong 下的 `O_APPEND`：读者可能短暂看到"已分配、尚未写完"的区域为 0；追加后 `lseek(fd, 0, SEEK_CUR)` 的位置以内核为准，可能不精确。
7. 缩短截断不是崩溃原子的（先截数据、后改长度）：两步之间崩溃 → 长度不变、被截区域读为 0。
8. 不同节点**并发**地 truncate 与 write 同一区域，可能得到"长度来自写、数据被截为 0"的结果；需要确定结果请加锁。
9. 所有副本同时掉电时，未 fsync 的数据可能丢失，即使曾被读到过（2.5）。
10. 客户端在提交长度前崩溃：它写入但未提交长度的数据在文件长度之外不可见；若之后别人把文件扩展到覆盖该区域，可能看到这段数据（等同本地文件系统崩溃后的部分写）。
11. 目录的 `st_size` = 条目数；inode 号永不复用、`generation` 恒为 0。
12. mtime/ctime 用元数据 leader 的时钟；节点间墙钟误差需 < 5 分钟（请运行 NTP）。
13. relatime 的 atime 更新是批量、尽力而为的：客户端崩溃或元数据 leader 切换时可能丢一次。
14. 阻塞等锁由客户端定期重试实现（50 ms 起，最长每 1 s 一次），**不保证先来先得**：竞争激烈时某个等待者可能等很久。
15. inotify/dnotify 只看得到本节点的变化；文件租约 `F_SETLEASE` 只在本节点有效。
16. 回收站（`trash`）：被删文件移进设置了 `trash` 的目录下的 `.wmfs-trash/`，**仍计入该子树的配额**；删除目录树时文件平铺进回收站，目录结构不保留；用普通 `mv` 移出即恢复。

### 3.4 不支持（返回明确的错误，而不是假装成功）

目录硬链接（`EPERM`）；`RENAME_WHITEOUT`（`EINVAL`）；`copy_file_range`/reflink（`EOPNOTSUPP`，内核自动回退为普通拷贝）；`fallocate` 的其他模式（`EOPNOTSUPP`）；`chattr` 标志（`ENOTTY`）；强制锁；跨节点共享可写 mmap（strong 下 `ENODEV`）。

## 4. 目录属性什么时候生效

所有策略都是目录属性（`wmfs set`），子树继承。"新文件"一律包括**截断到 0 的文件**（`O_TRUNC`、`cp` 覆盖已有文件、`truncate -s 0`）：截断到 0 时系统按当前生效属性重新安排这个文件的存储。

| 属性 | 对新文件 | 对已有文件 |
|---|---|---|
| `class`、`replicas`、`compress`、`encrypt` | 立即 | 由后台协调器迁移，进度见 `wmfs status`。**迁移完成之前，往已有文件里新写的数据仍按旧设置存放**（例如刚开加密时，已有文件的新写入仍是明文，直到它被转换）；**一直处于写打开状态的文件不会被转换**——`wmfs set` 时会提醒，`wmfs status` 单独列出这类文件的个数，跳过超过 24 小时会产生告警（ADR-0021） |
| `chunk`、`stripe`、`inline`、`checksum`、`locality` | 立即 | 不迁移（理念文档写的 checksum、locality 是"新数据"；因为这些参数属于文件的存储布局，已有文件的新写入沿用它原来的设置）；`locality` 对读的副本选择立即生效 |
| `quota`、`quota.<class>`、`qos`、`trash`、`audit` | 立即 | 立即 |
| `consistency`（及 `attr_ttl`） | 对之后新打开的文件 | 对之后新打开的文件；目录项/属性缓存时长立即按新值 |
| `tier`、`ttl` | 由后台任务按条件执行 | 同左 |
| `acl.default` | 新建的文件与目录 | 不改已有对象 |

设置时如果声明在当前集群无法满足（例如单节点上 `replicas=3`，或 `stripe` 大于可用的链数），设置照样成功，但会给出警告，见第 7 节。

## 5. 配额精度（ADR-0026）

- 配额是目录属性 `quota=<字节>[,soft=][,grace=][,files=][,quantum=]` 与按存储类的 `quota.<class>=…`，对整个子树生效，上级配额不能被子目录的 `inherit=false` 绕过。没写 `grace=` 时宽限期为 7 天，没写 `quantum=` 时为 64 MiB。
- **字节配额（quantum 额度模型）**：客户端每次向元数据服务申请一段写入额度（默认 64 MiB），越过额度前先提交已写长度并申请下一段；额度为 0 时这次 `write()` **立即**返回 `EDQUOT`（不是等到 close 才报）。
  - 遵守协议的客户端：用量最多超出硬限 `quantum × 同时向该子树写入的文件数`；**单个写者精确不超**。quantum 可逐目录调小（例如 `quantum=1M`）以收紧上界，代价是更多元数据请求。
  - 任何客户端（含不遵守协议的）：用量最多超出硬限 `16 × quantum`。
  - 多于 16 个写者同时逼近上限时，个别写者可能在 `fsync/close` 时收到 `EDQUOT`（数据未被接受，错误会如实报告）。
- **文件数配额**（`files=`）精确，在创建时检查。
- **软限 + 宽限期**：超过软限开始计时并产生事件；宽限期内按硬限，宽限期过后按软限拒绝增长；在操作时刻精确判定。
- **计量口径**：逻辑大小（普通文件 `st_size` 之和；稀疏文件按表观大小）；硬链接文件只在其主链接所在目录计一次；"删除后仍打开"的文件不计；回收站里的文件仍计入；写进副本但从未提交长度的数据不计入逻辑用量（只占物理空间，`wmfs status` 同时显示逻辑用量与各 target 的物理用量，差异可见）。
- 递归用量（`wmfs usage`）对任意目录常量时间可得，与配额使用同一份计数。
- 元数据 leader 切换不破坏上界：额度不是持久状态，每次都按已提交的用量重新计算。

## 6. 隔离承诺（理念文档 6.3 [固定]）

- vSSD 类的默认隔离手段是**独占物理盘或 namespace**（存储类 `devices.dedicated = true`，每块盘一个 target）。系统把每个 target 所在目录解析到**物理整盘或 NVMe namespace**（分区算它所在的整盘；LVM/dm/md 一直追到底下的物理盘；loop 设备或解析失败算"未知"）。只有一个类的物理盘与其他类完全不重合、且没有"未知"时，才显示"份额 + 尾延迟（以设备能力为限）"。同一块盘上的两个分区、同一个 PV 上的两个 LV，都算共用。
- **共用设备（或未知）时只承诺份额（mClock 的保底/权重/上限），不承诺尾延迟。** 声明了 `dedicated` 却实际共用时，产生 `isolation_downgraded` 告警。
- vHDD 类（`priority = low`，label 为 hdd 的类默认如此）只承诺容量、带宽份额与**低优先级**：在按权重分享的阶段，只有普通优先级的队列都没有可派发的请求时才轮到它（保底不受影响），**不承诺延迟**；HDD 类只适合顺序大块与冷数据，随机 IO 请放 NVMe 类。系统不会按热度自动把数据挪来挪去（只按目录属性 `tier` 与文件访问时间分层）。
- QoS 的数字是"成本单位"：一次 IO 的成本 = 1 + 字节数 / 128 KiB（4 KiB = 1，1 MiB = 9，4 MiB = 33），存储类里的 `iops_*` 与目录 `qos` 的 `r/l` 都按它计；`wmfs class show` 直接显示换算成带宽的结果。
- QoS 首发只在数据节点执行；目录或存储类上的保底与上限按该类的可用数据节点数**静态均分**到每个节点（没有跨节点协调）：负载不均时总保底可能达不到、总上限偏保守。元数据请求不做 QoS（ADR-0010）。
- cgroup io 隔离、NVMe WRR、NVM Sets、FDP 首发不做（ADR-0011）；唯一兑现的硬件隔离是整盘（或整 namespace）独占。
- 块设备（ublk 网关）首发不提供。

## 7. 故障与可用性

- **3 节点集群任意单节点宕机**：元数据 leader 切换约 1–3 s；数据链重配约 8–10 s（target 租约 8 s + 集群图传播）。期间客户端自动重试（同一个请求序号，保证恰好执行一次），应用只感到一次停顿，**除超时重试外没有错误**。
- 客户端总重试期限 = 挂载参数 `--op-timeout`（默认 120 s，类似 NFS hard 挂载）；超过才返回 `EIO`。
- 一条链的最后一个正常副本离线时，该链上的数据**不可用**（读写都等待重试，超时 `EIO`），系统不会用可能过期的副本顶替；dashboard 告警"链 X 等待最后的副本"。管理员可以 `wmfs chain force-serving` 明确接受可能的数据丢失。
- 元数据 2 个节点时没有高可用（保持 1 个 voter + 1 个 learner，`wmfs status` 警告）；推荐 1 个或 ≥ 3 个元数据节点。
- 同一台机器上的多个节点不构成真正的容错（`wmfs status` 与 dashboard 显示"故障域重叠"）。
- **连接层**（M1 起）：网络连接断开、对端重启时，客户端自动重连并按退避重试（10 ms 起、每次翻倍、最长 1 s，总期限见上），日志里记"连接断开 → 重连重试"；密钥不对等认证失败**不重试**，直接报 `AUTH_FAILED`。一个卡住、不读数据的客户端拖不慢服务端：它的连接在写不出去 5 秒后被断开，只影响它自己。
- **元数据（M3 起，单节点）**：元数据修改在返回之前已在本节点 fsync（一批一次 fsync，负载高时一批带走很多请求）；`kill -9`、或在落盘的任何一步崩溃之后重启，**已确认的修改一个不丢**（崩溃前没来得及确认的，重启后可能在、也可能不在——客户端用同一个请求序号重试，M4 起由去重表保证恰好执行一次）。元数据库本身读写出错、或内部检查发现不一致时，节点**立即退出**（fail-stop），不会带着写了一半的状态继续服务；重启后从日志恢复。重启后要等它重新当上就绪的 leader（通常不到 1 秒，`wmfs dev wait leader`）才接受请求，期间的请求自动重试。
- 客户端被冻结或失联超过会话租约（30 s）会被驱逐：之后它所有已打开的句柄返回 `EIO`，写回缓冲里未提交的数据丢失并在下一次 `write/fsync/close` 报告 `EIO`（不静默）；重新打开文件即可继续使用。
- 声明无法满足时（例如单节点上 `replicas=3`，或 `stripe=4` 但只有 2 条可用的链）：文件照常创建，但实际副本数 / 条带数较少；**不会静默**：`wmfs init`、server 启动日志、`wmfs mount` 的输出、`wmfs status` 的第一行、`wmfs get` 的 semantics 行（"replicas:声明3/实际1"）、`wmfs set` 时都会警告，dashboard 显示差距；加入节点后自动补齐（ADR-0016，待人类决定是否改为直接拒绝）。
- 集群里每个节点必须启用同一组会影响策略的插件（授权、配额、QoS、放置、变换、后台任务等）。插件配置与集群清单不一致的节点会**退出**并列出差异，而不是带着少一条规则的配置继续服务。

## 8. 安全边界（ADR-0009）

- 服务端强制授权：每个元数据请求都经过权限检查（POSIX 权限、ACL、路径限制）；数据请求凭元数据签发的、带过期时间的签名令牌。
- 客户端机器凭共享密钥（challenge-response，密钥不在网上传输）证明身份；**它声明的 uid/gid 只在该密钥允许的 uid 范围内被相信**，`root_squash` 把 root 映射为 nobody（类似 NFS AUTH_SYS + 主机密钥）。被攻破的客户端主机可以冒充其 uid 范围内的任何用户。客户端密钥不能冒充服务端（握手时核对角色）。
- 路径限制（path-caps）可以把一把密钥限制在若干子树内。
- 调试键空间（`wmfs debug kv`：元数据库里单独的一块调试区域，不碰文件系统的数据）只接受 admin key，且服务端 node.toml 里打开 `debug_ops` 才可用（`wmfs dev` 打开，`wmfs init` 默认关闭）。
- 管理 API（HTTP）：`/metrics` 与 `/api/v1/health` 不需要认证（只含指标与节点地址）；其余接口都要带签名，写操作只接受 admin key。故障注入接口（`/api/v1/failpoints`）只给测试用，只在 node.toml 里写了 `failpoints_api = true` 时存在（`wmfs dev` 默认打开，`wmfs init` 默认关闭）。
- **首发不加密网络流量（没有 TLS）**：只在可信网络中使用。管理 API 的写请求带签名与时间戳，**5 分钟之内被截获的请求可以被原样重放**，超过 5 分钟不行。
- 管理端口（HTTP）只应对可信网络开放：同一网络里的恶意程序可以用不发完的请求占住它的处理线程，让管理命令变慢或无响应（不会让节点崩溃，也绕不过签名；数据读写走另一个端口，不受影响）。首发接受这一限制（ADR-0030）。
- RDMA 下客户端永远拿不到服务端内存的访问钥匙；服务端之间互相信任（服务端之间的请求会带上发起方的钥匙）。服务端一侧的 RDMA 连接不开放远程读写，所以客户端即使猜到了地址与钥匙也读写不了服务端内存（由网卡保证；M2 起）。**rdma 传输未在本机验证**（本机没有可用的 RDMA 链路，见第 10 节）。
- 数据落盘加密（`encrypt=tenant:<名字>`，AES-256-GCM，每块随机 nonce）只加密 chunk 数据；开启加密的目录里新文件不再内联到元数据库；开启加密**之前**写入的内容，以及开启后、转换完成前往已有文件里新写的内容，在后台转换完成前仍是明文（一直写打开的文件不会被转换，第 4 节）；元数据库的空闲页里也可能残留旧明文，直到被覆盖。

## 9. 首发不支持（汇总）

纠删码（`ec`，二期）；快照（`snapshot`，二期——chunk 版本已从第一天按快照需要设计）；NFS / SMB / S3 / ublk 网关（二期插件）；内核客户端与 LD_PRELOAD 拦截库（客户端库与协议已留出复用接口）；跨地域复制；磁带 / HSM；WASM 用户策略（二期，策略求值点已预留，`wasm:` 开头的属性值会被拒绝）；跨节点共享可写 mmap；FUSE passthrough 与 io_uring；cgroup io / NVMe WRR / NVM Sets / FDP 隔离；跨节点协调的 QoS（dmClock）与元数据 QoS；元数据 follower 读；审计 open/read（`audit` 只记录修改类操作）；动态库插件中除授权以外的钩子（ADR-0012，待人类确认）。设置这些功能对应的属性会得到明确错误（`EOPNOTSUPP`"二期功能"），不会被静默接受。

## 10. 承诺的部署组合与本机验证范围

- **只承诺三个 profile 通过全套测试**（理念文档第 9 章）：`minimal`（单节点、TCP、不启用配额）、`hpc-rdma`（3 节点、RDMA、配额、QoS）、`nas-safe`（3 节点、replicas=3、回收站、审计）。**其他插件组合尽力而为**：能用，但没有经过全套测试。
- `hpc-rdma` 在没有真实 RDMA 设备的环境里标为**未验证**（本机只能用 Soft-RoCE 做功能测试；没有 Soft-RoCE 时整套显示 SKIP，发布说明不得声称支持）。本机按人类决定（2026-10-20）不做 RDMA 实机测试，因此 RDMA 在本机属于"未验证"。
- 本机只有一块 NVMe 系统盘，所有"节点"共享它：隔离承诺永远显示 shared，性能数字不代表多机部署；"RDMA 路径不低于 BeeGFS 的 80%"无法在本机验证（ADR-0015）。
- "多节点"是同一台机器上的多个进程：能验证协议与故障处理逻辑，但不是真正的机器级容错。
- 真实设备上的**掉电**持久性（fdatasync 与目录 fsync 的顺序是否在 ext4/XFS 上真的够）本机无法验证：测试用模拟掉电的存储后端检查"该 fsync 的地方都 fsync 了"，真实设备上的验证需要有 root 的 dm-log-writes 或 LazyFS 环境补做（ADR-0015）。
- 本机根分区是 ext4（推荐生产用 XFS，ADR-0008）。
