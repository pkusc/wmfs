# wmfs 语义承诺（对外文档）

> 状态：**accepted（人类于 2026-10-20 批准）**。本文是理念文档 10.3 要求的对外承诺：一致性模型、POSIX 放松清单、配额精度、隔离承诺、首发不支持的东西。权威设计见 [design.md](design.md)（3.1、3.9、6.3 等节）；本文与 design.md 冲突时以 design.md 为准并修正本文。
> 原则 7"诚实的语义"：做不到的不承诺；宁可拒绝操作，也不静默丢数据、静默降级或静默忽略策略。

---

## 1. 怎么查询你得到的语义

- `wmfs get <路径>`：列出该目录的生效属性及来源，最后一行固定是 `semantics:`，例如
  `semantics: consistency=cto attr_ttl=1s (来源 /); quota=quantum:64MiB overshoot<=64MiB*writers (来源 /home/alice); durability=replicas:声明3/实际1 fsync:all-replicas; isolation=shared-device(份额,不承诺尾延迟)`
  "实际"是这个目录下的新文件此刻能得到的副本数；声明与实际不同时，这一行之前还会多打印一行警告。
- `wmfs status <路径>`：第一行是集群警告（例如"有 3 条链少于声明副本数""故障域重叠"）；之后逐个属性列出声明、来源、实际与是否一致（例如 replicas 声明 3、实际 2 的文件数；配额用量与软限计时；QoS 保底欠额；审计消费者落后多少条），以及隔离承诺、后台迁移进度。
- `GET /api/v1/semantics`：本文要点与当前集群参数（租约时长、cap 有效期）。
- M7 起这些都可用（`wmfs get/status` 的路径可以是挂载点下的路径）。`wmfs status` 的"实际"先给**这个目录下的新文件此刻实际
  得到的值**（例如单节点上 replicas 声明 3、实际 1）；M9 起 replicas 另给子树里已有文件中**实际副本数少于声明**的个数（实际 = 它所在
  的链此刻正常服务的副本数，例如节点宕机、链降级时）；M11 起还有逐个已有文件的统计：class、replicas、compress、encrypt、chunk、
  stripe、inline、checksum 每个键数出子树里有多少已有文件与声明不同（前四个由后台协调器转换，另数出其中一直写打开、被跳过的；后四个
  标注"不迁移"）、位于降级链上的文件数与字节数，最后是协调器的进度与积压。一次最多看 100 万个 inode，看不完就在警告里明说统计不全。
  quota 与 `quota.<类>` 的"实际"是管着这个目录的各个配额此刻的用量与上限（软限的计时与宽限剩余），超了软限（含宽限已过）或超了硬限
  算不一致。M12 起：trash 的"实际"是它的回收站里的文件数与字节数，ttl 的是已经过期、还没被删掉的文件数，audit 的是审计消费者（`audit-log`
  游标）落后最新 changelog 的条数（落后就算不一致）。M13 起：qos 的"实际"是下发到每个节点的份额（按节点数均分之后）、隔离承诺与各节点
  报的保底欠额（有欠额就算不一致），tier 的是条件已经成立、还没迁过去的文件数。

## 2. 一致性模型

一致性等级是目录属性 `consistency`，取值 `cto`（默认，可带子键 `attr_ttl`，例如 `consistency=cto,attr_ttl=3s`）或 `strong`，对**之后新打开**的文件生效。

### 2.1 元数据（两种等级相同）

所有元数据操作（创建、删除、rename、属性、锁……）在元数据 leader 上**线性一致**：修改在多数派落盘并应用后才返回；读取先确认 leader 身份再读。rename 对所有观察者原子：要么旧名存在、要么新名存在。

### 2.2 `cto`（close-to-open，默认）

1. 写者 `close()` 成功返回后，**之后**在任何节点发起的 `open()` 一定看到该文件此前写入的全部数据、新长度与 mtime。
2. 文件打开期间，不保证看到其他节点的新写入；但每次读到的每个 chunk 都是某个已提交的版本，不会读到"写了一半"的数据，也不会"先读到新、后读到旧"。
3. 其他节点的创建、删除、rename、属性变化，最多 `attr_ttl`（目录属性，默认 1 s，范围 0–10 s；挂载参数 `--max-attr-ttl` 只能把它调得更小）后在本节点可见；`open()` 总会重新校验。
4. 本节点内：写后读总能读到自己的写。
5. 用 `O_DIRECT` 打开的文件，每次 `write()` 都同步写到所有副本并提交长度后才返回（与 strong 的写相同）。

### 2.3 `strong`

1. 客户端不缓存数据与属性（direct_io，属性 TTL 0）。
2. 每次 `read()` 先线性一致地取一次文件长度，再读数据；每次 `write()` 同步写到所有副本并同步提交长度后才返回。于是任意两个节点之间"写完立刻可读到"。单个 chunk（默认 4 MiB）内的读写线性一致；跨 chunk 的一次大写不是原子的（与本地文件系统相同，需要原子性请加锁）。
3. 跨节点 `O_APPEND`：每次追加的偏移由元数据服务原子分配，多个节点并发追加互不覆盖、按分配顺序排列。内核会把一次大的 `write()` 按 max_write（通常 1 MiB）切成几段、每段各自分配偏移，所以只有单次不超过这个大小的追加保证整条连续；更大的追加互不覆盖，但可能与别的节点的追加交错。`pwritev2(RWF_APPEND)` 不经文件的打开标志，wmfs 看不到，按内核给的偏移写（跨节点不保证互不覆盖）。
4. 跨节点共享可写 `mmap`：**拒绝**——strong 文件上任何 `MAP_SHARED` 映射（即使只读）返回 `ENODEV`；`MAP_PRIVATE` 可用。【ADR-0013，偏离理念文档 8.2"仅在 strong 下支持"】
5. strong 目录里新建的文件不会内联到元数据库；已有的内联小文件在第一次以写方式打开时先转成普通存储（对应用透明）。
6. 代价：每次写一次元数据提交（本机约 3–6 ms）。适合日志、共享状态等"协调为主"的负载，不适合大量小块随机写。

### 2.4 锁是同步点（两种等级都成立）

`fcntl` 字节范围锁与 `flock` 是集群范围的，存在复制状态里，元数据 leader 切换不丢锁（普通文件上的锁；目录上的锁只在本节点有效，3.3 第 18 条）。拿到锁时客户端丢弃该文件的本地缓存；释放锁前先把写入提交出去。所以用锁协调的程序在 cto 下也正确（与 NFS 相同）。持锁客户端失联时，只有在它被驱逐、且所有数据节点都已拒绝它之后，锁才会转交给别人。阻塞等锁（`F_SETLKW`、阻塞的 `flock`）由客户端定期重试实现（50 ms 起，最长每 1 s 一次）：**不保证先来先得**，竞争激烈时某个等待者可能等很久；等锁的进程再多也不会卡住挂载点。

### 2.5 持久性

| 操作返回 | 意味着 |
|---|---|
| 元数据操作（create、rename、setattr……） | 已在元数据多数派落盘 |
| cto 的 `write()` | 数据在本客户端的写回缓冲里（尚未离开本机） |
| cto 的 `close()` | 数据已到达链上全部副本的内存（页缓存）并提交了长度：**可见，但不保证落盘** |
| `fsync()` / `fdatasync()` / `O_SYNC` 写 | 链上全部副本已 `fdatasync`，长度已在元数据多数派落盘 |
| strong 的 `write()`、cto 下 `O_DIRECT` 文件的 `write()` | 已到达全部副本的内存并提交了长度（落盘仍需 fsync） |

**所有副本同时掉电**时，未 fsync 的数据可能丢失——即使它曾被读到过（文件大小可能已更新，丢失区间读为 0）。这与本地文件系统的 POSIX 语义相同；"有 3 个副本"不等于"不需要 fsync"。fsync 过的数据在所有副本上都已落盘，不会因为掉电丢失。（真实设备上的掉电行为本机无法验证，见第 10 节。）

## 3. POSIX 支持与放松清单

### 3.1 支持

普通文件、目录、符号链接（目标 ≤ 4096 字节）、硬链接（仅文件，每个文件 ≤ 1000 个）、fifo/socket/设备节点（只存元数据）；名字 1–255 字节；`rename`（含 `RENAME_NOREPLACE`、`RENAME_EXCHANGE`）；`chmod/chown/utimensat/truncate`；`fallocate` 模式 0；xattr（`user.*`、`security.*`、`trusted.*` 仅 root、POSIX ACL；每个文件合计 ≤ 64 KiB）；POSIX ACL（父目录有默认 ACL 时新建对象不应用 umask，符合 POSIX）；`fcntl` 字节范围锁与 `flock`；`O_APPEND/O_EXCL/O_TRUNC/O_DIRECT/O_SYNC/O_DSYNC`；`fsync/fdatasync`；稀疏文件；跨客户端"删除后仍打开"（打开者关闭前仍可读写）；`statfs`；`readdir/readdirplus`。

### 3.2 理念文档 8.2 的放松（原文对应）

1. `atime` 按 relatime 语义更新。
2. 跨节点共享可写 `mmap`：首发**任何等级都不支持跨节点一致**；strong 下明确拒绝（`ENODEV`），cto 下只有同一节点内一致（ADR-0013）。
3. 不支持强制锁；字节范围锁与 flock 支持。
4. 跨节点 `O_APPEND` 的顺序仅在 `consistency=strong` 下保证；cto 下由各节点内核按自己缓存的长度计算偏移。所以即使不是同时追加：另一个节点在属性缓存时长（默认 1 秒）内刚追加过时，本节点的 `O_APPEND` 也可能从旧的长度处写、覆盖它刚追加的内容。多个节点追加同一个文件请用 strong 目录（M12 起）。
5. `cto` 模式下，另一节点的写入在本节点下一次 `open` 后可见。
6. 配额在客户端缓存写回前可能短暂超限，超限幅度有上界并可配置（第 5 节）。

### 3.3 本设计新增的放松（ADR-0014，人类于 2026-10-20 批准）

1. cto 下目录项与属性缓存最长 `attr_ttl`（目录属性，默认 1 s，受挂载参数 `--max-attr-ttl` 限制）陈旧（M7 起可以按目录设置，例如
   `wmfs set /proj consistency=cto,attr_ttl=0s` 让这棵子树完全不缓存属性）。
2. `flock` 与 `fcntl` 锁共用一个锁空间（FUSE 库没有把"这是 flock"的标志传给文件系统）：同一进程对同一文件混用二者会互相冲突（Linux 本地文件系统上二者互不影响）。
3. 阻塞的 `F_SETLKW` 不能被有处理函数的普通信号打断；致命信号（`kill -9`，或没有处理函数的 SIGINT/SIGTERM）会在 1 秒内让等待结束、进程正常退出。所以靠信号实现的等锁超时（`flock -w <秒>`、`alarm()`）不起作用，会一直等到拿到锁。
4. 不做死锁检测（不返回 `EDEADLK`）。
5. 通过 `mmap` 写入的数据，配额错误在写回阶段发生，于 `msync/fsync/close` 报告。
6. strong 下的 `O_APPEND`：读者可能短暂看到"已分配、尚未写完"的区域为 0；追加后 `lseek(fd, 0, SEEK_CUR)` 的位置以内核为准，可能不精确。
7. 缩短截断不是崩溃原子的（先截数据、后改长度）：两步之间崩溃 → 长度不变、被截区域读为 0。
8. 不同节点**并发**地 truncate 与 write 同一区域，可能得到"长度来自写、数据被截为 0"的结果；需要确定结果请加锁。
9. 所有副本同时掉电时，未 fsync 的数据可能丢失，即使曾被读到过（2.5）。
10. 客户端在提交长度前崩溃：它写入但未提交长度的数据在文件长度之外不可见；若之后别人把文件扩展到覆盖该区域，可能看到这段数据（等同本地文件系统崩溃后的部分写）。
11. 目录的 `st_size` = 条目数；inode 号永不复用、`generation` 恒为 0（M4 起）。
12. mtime/ctime 用元数据 leader 的时钟；节点间墙钟误差需 < 5 分钟（请运行 NTP）。
13. relatime 的 atime 更新是批量、尽力而为的：客户端崩溃或元数据 leader 切换时可能丢一次。
14. 阻塞等锁由客户端定期重试实现（50 ms 起，最长每 1 s 一次），**不保证先来先得**：竞争激烈时某个等待者可能等很久。
15. inotify/dnotify 只看得到本节点的变化；文件租约 `F_SETLEASE` 只在本节点有效。
16. 回收站（`trash`）：被删文件移进设置了 `trash` 的目录下的 `.wmfs-trash/<uid>/`（`<uid>` 是文件的属主；只有属主与 root 看得到、恢复得了，人类于 2026-11-07 决定，ADR-0043 第 1 条），**仍计入该子树的配额**；删除目录树时文件平铺进回收站，目录结构不保留；用普通 `mv` 移出即恢复。回收站只管文件的最后一个链接：还有别的硬链接的文件，`rm` 只去掉这个名字、不进回收站。
17. 已经打开的文件，之后被去掉读写权限（chmod、chown、改 ACL）：**属主**自己的句柄照常可用（与 NFS 相同；git、cp 先建只读文件再往里写也靠这一点）；**其他用户**之前打开的句柄，之后可能报 `EACCES`——写在下一次提交长度（写回、fsync、close）时，读在令牌续期时（打开约 8 分钟之后）。（ADR-0036，人类于 2026-10-22 决定）
18. 目录上的 `flock`/`fcntl` 锁只在本节点有效：内核 FUSE 不把目录上的锁请求交给文件系统，到不了 wmfs。要跨节点互斥，请锁目录里的一个普通文件。（ADR-0043 第 4 条）

### 3.4 不支持（返回明确的错误，而不是假装成功）

目录硬链接（`EPERM`）；跨配额范围的硬链接（`link`，以及有多个硬链接的文件跨配额范围 `rename`，回 `EXDEV`，同 XFS 的项目配额；`mv` 会自动改为复制，ADR-0041）；`RENAME_WHITEOUT`（`EINVAL`）；`copy_file_range`/reflink（`EOPNOTSUPP`，内核自动回退为普通拷贝）；`fallocate` 的其他模式（`EOPNOTSUPP`）；`chattr` 标志（`ENOTTY`）；强制锁；跨节点共享可写 mmap（strong 下 `ENODEV`）。

## 4. 目录属性什么时候生效

所有策略都是目录属性（`wmfs set`），子树继承。"新文件"一律包括**截断到 0 的文件**（`O_TRUNC`、`cp` 覆盖已有文件、`truncate -s 0`）：截断到 0 时系统按当前生效属性重新安排这个文件的存储。

| 属性 | 对新文件 | 对已有文件 |
|---|---|---|
| `class`、`replicas`、`compress`、`encrypt` | 立即 | 由后台协调器迁移，进度见 `wmfs status`。**迁移完成之前，往已有文件里新写的数据仍按旧设置存放**（例如刚开加密时，已有文件的新写入仍是明文，直到它被转换）；**一直处于写打开状态的文件不会被转换**——`wmfs set` 时会提醒，`wmfs status` 单独列出这类文件的个数，跳过超过 24 小时会产生告警（ADR-0021） |
| `chunk`、`stripe`、`inline`、`checksum`、`locality` | 立即 | 不迁移（理念文档写的 checksum、locality 是"新数据"；因为这些参数属于文件的存储布局，已有文件的新写入沿用它原来的设置）。`locality` 只管新文件放在哪、不管读：所有文件的读都先找与客户端同一台主机上的副本，其余按 chunk 分散到各个副本（ADR-0044 第 1 条） |
| `quota`、`quota.<class>`、`qos`、`trash`、`audit` | 立即 | 立即 |
| `consistency`（及 `attr_ttl`） | 对之后新打开的文件 | 对之后新打开的文件；目录项/属性缓存时长立即按新值 |
| `tier`、`ttl` | 由后台任务按条件执行 | 同左（`tier`：已经分层过去的文件留在目标类里，之后再被读写也不会被挪回来；想挪回去请改目录的属性） |
| `acl.default` | 新建的文件与目录 | 不改已有对象 |

设置时如果声明在当前集群无法满足（例如单节点上 `replicas=3`，或 `stripe` 大于可用的链数），设置照样成功，但会给出警告，见第 7 节。

M13 起能设置的属性：`class`、`replicas`、`chunk`、`stripe`、`inline`、`checksum`（`crc32c`、`xxh3`、`blake3`）、`compress`、`encrypt`、`consistency`
（`cto` 与 `attr_ttl`，或 `strong`）、`inherit`、`quota`、`quota.<类>`、`acl.default`、`trash`（`off` 或保留期，最长 365d）、`ttl`（`off` 或时长，
按 mtime）、`audit`（`off`、`on`，可加过滤 `ops=create+unlink`、`uids=1000+1001`），以及 M13 的 `qos`（`r=<保底>,w=<权重>,l=<上限>[,bw=<字节/秒>][,burst=<时长>]`，
单位见第 6 节；或 `qos=<存储类名>`：借用那个类的 QoS 包络，跟着那个类变——改了那个类的 `[qos]`，借用它的目录约 1 s 内用上新份额；`wmfs get` 显示类名；被借用的类不能删，ADR-0044 第 2 条）、`tier`（`<from>-><to>:<条件>`，条件 `idle>时长`、`age>时长`、
`size>尺寸`，用 `&` 连接）、`locality`（`prefer-client`：新文件的写入口（链头）优先放在客户端所在的节点上；没有以那个节点为链头的链时（例如它重启过，见第 6 节），优先放在有一个副本在那个节点上的链上，再没有就按普通规则放；`any`）。还没有实现的只剩二期功能（`ec`、
`snapshot`），设置时**明确报错**（`EOPNOTSUPP`），拼错的属性名报"未知属性"，没有插件消费的属性（例如 minimal 部署停用了 mclock，`qos`
就没有插件消费）也被拒绝——都不会被静默接受。存储类用 `wmfs class create|update|list|show|delete` 管理（TOML 定义，design.md 6.1）：
`update` 只改 QoS 时只下发新份额、不搬数据，改副本数或分层规则时后台从根整树转换，不能改设备标签与独占（请新建一个类再改目录的 `class`）；
首发只能删没用过的类。

后台转换（M11 起）：`wmfs set` 了 `class`、`replicas`、`compress`、`encrypt` 之后，协调器在后台把已有文件逐个换到新布局（限速，
`wmfs task set reconciler bw=…`；`wmfs task pause|resume reconciler` 暂停与恢复；元数据 leader 换了从断点接着做）。换布局时内容不变
（`change_id`、`ctime` 也不变）；转换途中有人写这个文件，这一次转换作废、稍后重做，写的数据不会丢。系统经客户端的会话心跳（约 3 秒一次）
才知道谁写打开着什么：**刚写打开、还没报上来的文件照样可能被转换**，写者随后的写由客户端自动重写到新布局，同样不会丢。

## 5. 配额精度（ADR-0026）

- 配额是目录属性 `quota=<字节>[,soft=][,grace=][,files=][,quantum=]` 与按存储类的 `quota.<class>=…`，对整个子树生效，上级配额不能被子目录的 `inherit=false` 绕过。没写 `grace=` 时宽限期为 7 天，没写 `quantum=` 时为 64 MiB。
- **字节配额（quantum 额度模型）**：客户端每次向元数据服务申请一段写入额度（默认 64 MiB），越过额度前先提交已写长度并申请下一段；额度为 0 时这次 `write()` **立即**返回 `EDQUOT`（不是等到 close 才报）。
  - 遵守协议的客户端：用量最多超出硬限 `quantum × 同时向该子树写入的文件数`；**单个写者精确不超**。quantum 可逐目录调小（例如 `quantum=1M`）以收紧上界，代价是更多元数据请求。
  - 任何客户端（含不遵守协议的）：用量最多超出硬限 `16 × quantum`。
  - 多于 16 个写者同时逼近上限时，个别写者可能在 `fsync/close` 时收到 `EDQUOT`（数据未被接受，错误会如实报告）。
- **文件数配额**（`files=`）精确，在创建时检查。
- **软限 + 宽限期**：超过软限开始计时并产生事件；宽限期内按硬限，宽限期过后按软限拒绝增长；在操作时刻精确判定。
- **计量口径**：逻辑大小（普通文件 `st_size` 之和；稀疏文件按表观大小）；硬链接文件只在其主链接所在目录计一次；"删除后仍打开"的文件不计；回收站里的文件仍计入；写进副本但从未提交长度的数据不计入逻辑用量（只占物理空间，`wmfs status` 同时显示逻辑用量与各 target 的物理用量，差异可见）。
- 硬链接不能跨配额范围（第 3.4 节），遗留一个缺口：给已经有跨目录硬链接的目录树新设配额、或把含多链接文件的目录 rename 到另一个配额范围之后，删掉主链接时用量照搬到其他链接所在的目录，不做配额检查。
- 递归用量（`wmfs usage`）对任意目录常量时间可得，与配额使用同一份计数；M10 起它另外列出管着这个目录的每个配额（用量 / 硬限、软限与宽限剩余、文件数、quantum）。越过软限时 changelog 里记一条 `PolicyViolation`（`kind=quota_soft`）。
- 元数据 leader 切换不破坏上界：额度不是持久状态，每次都按已提交的用量重新计算。

## 6. 隔离承诺（理念文档 6.3 [固定]）

- vSSD 类的默认隔离手段是**独占物理盘或 namespace**（存储类 `devices.dedicated = true`，每块盘一个 target）。系统把每个 target 所在目录解析到**物理整盘或 NVMe namespace**（分区算它所在的整盘；LVM/dm/md 一直追到底下的物理盘；loop 设备或解析失败算"未知"）。只有一个类**声明了 `dedicated = true`**、它的物理盘与其他类（包括其他类已有的数据所在的盘）完全不重合、且没有"未知"时，才显示"份额 + 尾延迟（以设备能力为限）"（没声明独占的类随时可能有别的类建在同一批盘上，碰巧不共用也不承诺；ADR-0044 第 3 条）。同一块盘上的两个分区、同一个 PV 上的两个 LV，都算共用。本机只有一块盘，所以永远显示 shared。
- **共用设备（或未知）时只承诺份额（mClock 的保底/权重/上限），不承诺尾延迟。** 声明了 `dedicated` 却实际共用时，产生 `isolation_downgraded` 告警。
- `dedicated = true` 的类**拿走**打了它的标签的 target：别的类的新文件从此不放在这些盘上；可别的类**已经**建在这些盘上的链与数据还留着，这时这个类如实显示 shared（并告警 `isolation_downgraded`）。所以要真正独占，**dedicated 类要在它的盘被别的类用上之前建好**：先 `wmfs class create`，再加入打了这个标签的 target（`wmfs join … --target <路径>:<标签>`）。会让别的类一个 target 也不剩的新建（例如 `label = "*"`）回 `EINVAL`（ADR-0044 第 4 条）。
- 存储类的 `latency_target` **只测量与告警，不承诺**：某个节点上这个类的客户端请求最近 10 s 的 p99 延迟连续 10 s 超过它时，changelog 里记一条 `PolicyViolation`（`kind=latency_target_exceeded`），回落之后再超再记（ADR-0044 第 5 条）。
- vHDD 类（`priority = low`，label 为 hdd 的类默认如此）只承诺容量、带宽份额与**低优先级**：在按权重分享的阶段，只有普通优先级的队列都没有可派发的请求时才轮到它（保底不受影响），**不承诺延迟**；HDD 类只适合顺序大块与冷数据，随机 IO 请放 NVMe 类。系统不会按热度自动把数据挪来挪去（只按目录属性 `tier` 与文件访问时间分层）。
- QoS 的数字是"成本单位"：一次 IO 的成本 = 1 + 字节数 / 128 KiB（4 KiB = 1，1 MiB = 9，4 MiB = 33），存储类里的 `iops_*` 与目录 `qos` 的 `r/l` 都按它计；`wmfs class show` 直接显示换算成带宽的结果。
- QoS 首发只在数据节点执行；目录或存储类上的保底与上限按该类的可用数据节点数**静态均分**到每个节点（没有跨节点协调）：负载不均时总保底可能达不到、总上限偏保守。一个文件的写只经过它的链头节点，所以单个文件的写入速度受"每节点份额"限制（例如 `iops_max = 300`、3 个节点：每节点 100，1 MiB 的写成本 9，约 11 MiB/s）。重启过的节点在每条链上都排到末尾，首发不会把写入口（链头）调回均匀：几个节点轮流重启之后，链头可能都集中在一个节点上，这时一个类的写只能用到它在那个节点上的份额（ADR-0044 第 8 条；链头自动均衡留到二期）。元数据请求不做 QoS（ADR-0010）。后台任务（协调器迁移、scrub、重同步）的数据请求进一个低优先级队列，受节点级后台限速。
- cgroup io 隔离、NVMe WRR、NVM Sets、FDP 首发不做（ADR-0011）；唯一兑现的硬件隔离是整盘（或整 namespace）独占。
- 块设备（ublk 网关）首发不提供。

## 7. 故障与可用性

- **3 节点集群任意单节点宕机**：元数据 leader 切换约 1–3 s；数据链重配约 8–10 s（target 租约 8 s + 集群图传播；宕的节点恰好也是元数据 leader 时约 10–13 s：先选出新 leader，新 leader 再等一个 target 租约才判定它离线，ADR-0040）。期间客户端自动重试（同一个请求序号，保证恰好执行一次），应用只感到一次停顿，**除超时重试外没有错误**。
- 客户端总重试期限 = 挂载参数 `--op-timeout`（默认 120 s，类似 NFS hard 挂载）；超过才返回 `EIO`。
- 一条链的最后一个正常副本离线时，该链上的数据**不可用**（读写都等待重试，超时 `EIO`），系统不会用可能过期的副本顶替；dashboard 告警"链 X 等待最后的副本"。管理员可以 `wmfs chain force-serving` 明确接受可能的数据丢失。
- 元数据 2 个节点时没有高可用（保持 1 个 voter + 1 个 learner，`wmfs status` 警告）；推荐 1 个或 ≥ 3 个元数据节点。
- 同一台机器上的多个节点不构成真正的容错（`wmfs status` 与 dashboard 显示"故障域重叠"）。
- **连接层**（M1 起）：网络连接断开、对端重启时，客户端自动重连并按退避重试（10 ms 起、每次翻倍、最长 1 s，总期限见上），日志里记"连接断开 → 重连重试"；密钥不对等认证失败**不重试**，直接报 `AUTH_FAILED`。一个卡住、不读数据的客户端拖不慢服务端：它的连接在写不出去 5 秒后被断开，只影响它自己。
- **元数据（M3 起，单节点）**：元数据修改在返回之前已在本节点 fsync（一批一次 fsync，负载高时一批带走很多请求）；`kill -9`、或在落盘的任何一步崩溃之后重启，**已确认的修改一个不丢**（崩溃前没来得及确认的，重启后可能在、也可能不在——客户端用同一个请求序号重试，M4 起由去重表保证恰好执行一次）。元数据库本身读写出错、或内部检查发现不一致时，节点**立即退出**（fail-stop），不会带着写了一半的状态继续服务；重启后从日志恢复。重启后要等它重新当上就绪的 leader（通常不到 1 秒，`wmfs dev wait leader`）才接受请求，期间的请求自动重试。
- **命名空间（M4 起，单节点）**：创建、删除、改名、硬链接、属性、xattr 等元数据修改都带一个请求序号（seq），网络出问题时客户端用**同一个序号**重试，服务端的去重表把第一次的结果原样返回——所以"创建目录"不会因为回复丢了、重试而报"已存在"（`wmfs fs mkdir --verbose` 能看到"超时重试 seq=… → 去重命中"）。rename 对所有观察者原子：任何时刻要么旧名存在、要么新名存在。权限按 POSIX 权限位检查（属主 / 属组 / 其他人、粘滞目录、chmod/chown 只有属主或 root），M10 起扩展 ACL 也按 POSIX.1e 判定（命名用户、命名组、mask；`setfacl`/`getfacl` 在挂载点上直接可用，目录属性 `acl.default` 给子树里新建的文件一个默认 ACL）。客户端声明的 uid 只在它的密钥允许的范围内被相信，`root_squash` 把 root 映射成 nobody（65534）。
- **数据（M5 起，单节点）**：
  - **校验**：文件数据按 4 MiB 切成 chunk 存在数据节点的 target 目录里，每个 64 KiB 块带一个 crc32c 校验和；读的时候逐块校验，**校验不过就返回 `EIO`，绝不返回错误的数据**（单副本时没有别的副本可以拿来修复，诚实报错；把坏掉的那个 chunk 整个覆盖写、或把文件截断到这个 chunk 的开头之前，之后照常可用。多副本时坏块会从好的副本修好；万一**全部副本**的这个 chunk 都坏了、连块表头也读不出，就只能把文件截断到 0（或用 `O_TRUNC` 覆盖写）或删掉它来恢复，ADR-0042 第 6 条）。
  - **崩溃与掉电**：修改 chunk 时不碰旧文件：先写一个新文件，写完再用一次 `rename` 替换，所以无论在哪一步崩溃或掉电，读到的要么是旧版本、要么是新版本，不会是"写了一半"的数据（重启时清掉没写完的新文件）；`fsync` 过的数据在掉电后仍在（2.5）。
  - **小文件**：≤ 64 KiB 的小文件内容直接存在元数据里（open 一次往返就拿到内容），文件写大时由服务端自动转成普通存储——只有写权限、没有读权限的用户也能正常往里写，而小文件的内容只给有读权限的人。
  - **令牌**：数据节点只凭元数据签发的、带过期时间的签名令牌放行读写（有效期 10 分钟，对节点间墙钟误差容忍 5 分钟）：令牌被篡改、过期、不属于这个文件或这条链、权限不够、或它所属的会话已被驱逐，一律拒绝。
  - **上限**：target 写到容量上限（node.toml 的 `[[target]] capacity`；`wmfs dev` 默认 20 GiB）时写入返回 `ENOSPC`。单个文件最大 = chunk 大小 × 2³²（默认 4 MiB 的 chunk 是 16 PiB），把文件改长或写过这个长度返回 `EFBIG`。
  - **回收**：截断到 0 或覆盖写换下来的旧数据在宽限期（默认 60 s）之后由后台 gc 删除（这之后，打开得早、还在读旧内容的程序读到的是截断之后的内容，close-to-open 允许，2.2）；后台转换换下来的旧数据（M11）还要等**没有人打开着这个文件**才删：转换之前就打开着它的程序照样读得到，都关掉之后再删；删除后仍被打开的文件等所有打开者都关闭之后才删数据。没能正常关闭会话的客户端（例如节点重启那一刻正在跑的 `wmfs fs put`）在会话租约（30 s）到期、被驱逐之后不再挡着回收（M10）。
- **挂载（M6 起，单节点）**：`wmfs mount`（或 `wmfs dev mount`）把 wmfs 挂成一个普通目录，`cp`、`diff`、`dd`、`md5sum`、`git` 等普通程序直接在上面用。
  - 两个挂载点（两个客户端）之间是 close-to-open（2.2）：一边 close 之后，另一边**之后**的 open 一定看到新内容与新长度，包括在 1 秒的属性缓存窗口内（`O_APPEND` 的写入偏移除外，见 3.2 第 4 条）；目录项与属性最多陈旧 1 秒。
  - `write()` 先进本客户端的写回缓冲，close（或 fsync、写满一个 4 MiB 的 chunk、数据放了超过 5 秒）时才写到数据节点并提交长度；**写回失败会在之后的 write、fsync 或 close 的返回值里报告**（例如 `EIO`），数据不会被悄悄丢掉。挂载进程在提交长度之前崩溃时，这部分数据在文件长度之外不可见（3.3 第 10 条）。用 `O_DIRECT` 打开的文件每次 `write()` 都同步写到全部副本并提交长度才返回。
  - 被删除但仍打开的文件可以一直读写到关闭；挂载进程收到 SIGTERM（或 `wmfs dev down`）时先把全部数据写出去再卸载。
  - `fcntl` 字节范围锁与 `flock` 是集群范围的（M12 起；M12 之前只在本节点有效），见 2.4 与下面的"锁、strong、回收站（M12 起）"。
    `copy_file_range` 返回 `EOPNOTSUPP`（内核自动退回普通拷贝），`chattr` 返回 `ENOTTY`。
  - 本机没有开 `user_allow_other`，所以一个挂载点只有挂载它的用户能访问；多用户的演示用 `wmfs fs --as-uid` 与容器（容器里以 root 挂载）。
- 客户端被冻结或失联超过会话租约（30 s）会被驱逐：之后它所有已打开的句柄返回 `EIO`，写回缓冲里未提交的数据丢失并在下一次 `write/fsync/close` 报告 `EIO`（不静默）；重新打开文件即可继续使用（客户端自动建立新会话）。驱逐分两步（M10）：先把会话拉黑（数据节点拿到新的集群图之后拒绝它的令牌），等每个数据节点都确认收到、或已经因为失联而自我隔离之后，才释放它持有的锁——它失联之前发出的写不可能在锁交给别人之后才落地。`wmfs session list` 列出全部会话与 24 小时内被驱逐的；`wmfs session evict` 手动驱逐。客户端距最近一次成功续租超过 0.8 × 30 s 时先暂停所有请求（含读）、等续租结果，所以它自己总比服务端先停。
- **目录属性与递归用量（M7 起）**：`wmfs set/get/unset`（属性沿目录树继承，`wmfs get` 显示每个值从哪一层来、最后一行 `semantics:`）；
  `wmfs usage <目录>` 常量时间给出子树的字节数（普通文件的逻辑大小之和，硬链接只计一次、"删除后仍打开"的不计）、文件数与子目录数；
  所有属性变更都写进 changelog（`wmfs changelog tail`，外部程序可以长轮询并提交自己的游标，至少一次投递）；集群运行参数（租约时长、
  `epoch_gc_grace` 等）用 `wmfs cluster set` 修改，全集群一致。管理命令只由元数据 leader 回答，命令行自动跟随。
  目录最多嵌套 65 536 层，更深处的操作返回 `EIO`（这个上限用来发现损坏的父目录指针；Linux 一条路径最长 4096 字节，按路径最多约 2048 层，ADR-0038）。
- **元数据三副本（M8 起）**：3 个或更多节点时，元数据（目录、文件名、属性、≤ 64 KiB 的小文件内容）有 3 个副本，每个修改在多数副本
  fsync 之后才确认。`kill -9` 元数据 leader 后约 1–3 s 选出新 leader，客户端用同一个请求序号自动重试，应用只感到一次停顿、**没有错误**
  （`scripts/accept.sh M8` 在 3000 次 mkdir 的循环中途杀 leader、连续 10 轮杀 leader）；正常停止（SIGTERM、`wmfs dev down`）的 leader 先把
  leader 让出去。被杀的节点重启后自动追上（落后太多时从 leader 下载一份快照）。新节点用 `wmfs join` 加入：先当只学习、不投票的 learner，
  追上之后一次变成 3 个 voter，不经过"2 个 voter、坏一个就不可用"的状态；`wmfs node list` 显示谁是 leader、各节点是否追平，
  `wmfs debug meta-hash` 比较各副本的状态。管理命令（`--cluster` 或 `WMFS_CLUSTER` 给多个地址）在某个节点停了、或 leader 换了时，选出新 leader 之后
  自动换到它；正在选举的那 1–2 秒里，一次性的管理命令可能报 `not_leader`，重试即可（`wmfs changelog tail -f` 会自己等）。
- **文件数据多副本（M9 起，链式复制）**：`replicas=3`（`/home` 的默认）的文件数据存 3 份，分别在 3 个节点上（一个节点一份：
  故障域 = 节点）。写从链头进、依次传到链尾，**全部副本都提交之后**才确认给写者；读可以去任何一个正常服务的副本，读到的永远是某个已
  提交的版本，不会"先读到新的、后读到旧的"（CRAQ）。
  - 写的过程中任一节点被 `kill -9`：应用的写照常成功，只是停顿一会儿（数据链重配约 8–10 s：target 租约 8 s + 集群图传播；宕的节点恰好也是元数据 leader 时约 10–13 s），内容一致
    （`scripts/accept.sh M9` 在写 2 GiB 的途中杀节点、比对 md5，并记下客户端最长的停顿）。期间副本少了一份：`wmfs status` 第一行起
    警告链降级，并给出"replicas 声明 3、实际 2"的文件数。
  - 节点回来之后先以 **Syncing** 身份重新同步（从链上最后一个正常服务的副本拷差异，期间照样接收新写、但不对外服务读），拷完才变回
    **Serving**；`wmfs dev wait chains-serving` 等的就是这一刻，之后 `wmfs status` 的差距归零。**任何重启都这样**，所以重启时丢掉的半截
    数据永远不会被读到。
  - 数据节点连续 6.4 s 联系不上元数据 leader 就自己停止服务读写（`FENCED`，客户端换副本或稍后重试），leader 等满 8 s 才把它移出链：
    不会有两边同时服务（运行中调小 `target_lease` 时，旧租约期满之前仍按旧值判定，ADR-0038）。
  - **一条链的最后一个正常副本离线时**，这条链上的数据不可用（读写都等待重试，超时 `EIO`），系统**不会**用可能过期的副本顶替；
    集群警告与 `wmfs status` 显示"链 X 等待最后的副本"。那个副本回来之后照常可用；它再也回不来时，管理员可以
    `wmfs chain force-serving <链> <target> --i-accept-data-loss` 明确接受可能的数据丢失（写 changelog）。
  - `fsync` 过的数据在链上**每个**副本上都已落盘；没 fsync 的写如果**所有副本同时掉电**可能丢失（即使曾被读到过），与本地文件系统的
    语义相同（2.5）。
  - 3 节点的开发集群里 3 个"节点"在同一台机器上：故障域重叠，这不是真正的容错（警告里写明）。
- **后台修复与清理（M11 起）**：
  - **scrub**：每个数据节点每 24 小时（`wmfs task run scrub` 马上来一轮，默认限速 50 MiB/s）把自己的每个副本读一遍、核对校验和；
    坏了就从同一条链上另一个正常的副本拷一份好的装上，changelog 记 `ChecksumRepaired`；一个好副本也没有（例如单副本、或全部副本都坏了）
    就**如实上报** `DataLossDetected`，之后读它照旧返回 `EIO`，不假装没事。平时读到坏块时客户端会换别的副本读，数据节点马上开始修它
    （不等 scrub 的下一轮），修好或修不了同样记进 changelog。只做数据的节点（不在元数据 raft 里，第 4 个节点起）收不到
    `wmfs task run/pause/set`，一直按默认值跑。
  - 丢了数据的文件（`DataLossDetected`）后台转换不了：它上面的目录改了 `class`、`replicas`、`compress` 或 `encrypt` 之后，
    协调器的积压一直不为 0（`wmfs task list` 看得到，`wmfs dev wait task-idle reconciler` 等不到），直到把这个文件截断到 0
    （含 `O_TRUNC` 的覆盖写）或删掉。
  - **坏盘**：一个 target 连续 3 次提交失败（多半是盘坏了）就自动变成只读，被移出写路径（链上补上别的副本），之后的写照常成功；重启节点
    后它重新加入。
  - **gc**：除了旧数据与删除后的文件，还清理已经关掉的会话留下的请求去重记录、所有消费者都读过（或超过 7 天、超过 1000 万条）的
    changelog（更早的读回 `410 Gone`，缺口是显式的），以及数据节点上元数据里已经没有的数据（例如节点离线时错过的删除，每 10 分钟查一次，
    只删超过 1 小时的）。
  - 后台任务的进度、速率与积压：`wmfs task list`（连不上的节点显示成连不上）；`wmfs dev wait task-idle <任务>` 等它这一轮做完——
    连不上的节点不算做完，一直等到超时；只做数据的节点收不到运行请求，对它们只等这一轮做完、积压为 0。
- **锁、strong、回收站（M12 起）**：
  - **锁**：`fcntl` 字节范围锁与 `flock` 在所有挂载点之间互斥（2.4；`F_GETLK` 也看得到别的挂载持有的锁，"到文件尾"的锁回 `l_len = 0`，`l_pid` 只在持锁者与你在同一台机器上时有意义）。
    目录上的锁例外：只在本节点有效（3.3 第 18 条；要跨节点互斥，锁目录里的一个普通文件）。
    进程关掉文件（任何一个 fd）时释放它在这个文件上的 `fcntl` 锁，`flock` 随最后一个 close 释放；挂载进程退出（会话关闭）时释放它的全部锁。
    `F_SETLKW` 与阻塞的 `flock` 由挂载进程在后台定期重试（50 ms 起、最长每 1 s 一次），等锁的进程再多，挂载点上别的操作照样立即响应；
    等锁的进程被 `kill -9` 时在下一次重试（≤ 1 s）时结束等待、不会拿到锁。挂载进程被冻住或失联时，它持有的锁要等它的会话被驱逐、所有
    数据节点都已拒绝它之后（约 30–40 s）才转给别人。挂载进程被冻住（SIGSTOP）期间，这个挂载点上的**任何** close 都要等它恢复——包括
    只读打开的 fd、子进程退出时自动关掉的继承来的 fd：close 要经挂载进程释放锁（M10 时只读打开的不经它，M12 起都经它）。
  - **strong**：`wmfs set <目录> consistency=strong` 之后新打开的文件按 2.3：不缓存、写完别的挂载点立即读到、跨节点 `O_APPEND` 互不覆盖
    （单次不超过 max_write、通常 1 MiB 的追加整条连续，2.3 第 3 条）、共享可写 mmap 回 `ENODEV`；目录里的 inline 小文件第一次写打开时
    转成普通存储（只读打开照旧，后台协调器的全量扫描也会把它们转出）。strong 下 `O_APPEND` 分配的区间精确检查配额（超了这次 `write()`
    立即 `EDQUOT`、长度不变）。
  - **回收站**（`trash=<保留期>`，ADR-0014 放松 ⑯）：`rm` 与被 `mv` 覆盖掉的文件移进设了 `trash` 的目录下的 `.wmfs-trash/<uid>/`，
    `<uid>` 是文件的属主（不是删它的人：root 删了 alice 的文件，它在 alice 的子目录里）。这个子目录 0700、属于他，`.wmfs-trash` 本身
    0711：只有属主与 root 看得到、恢复得了，别人也列不出有哪些用户（同 Linux 桌面的 `.Trash-<uid>`；ADR-0043 第 1 条）。名字
    `<unix 秒>-<inode 号>-<原名>`，xattr `user.wmfs.origin` 记着原路径；用普通的 `mv` 移出来就恢复了（`mv .wmfs-trash/$(id -u)/<名字> <原路径>`）；
    回收站里再 `rm` = 真删；到期后由后台任务 trash-expire 真删（还有人打开着就等他们关闭再回收数据）。还有别的硬链接的文件，`rm` 掉其中
    一个名字时只删这个名字、不进回收站（数据还在别的名字下）。回收站里的文件仍计入设了 `trash` 的那棵子树的配额（中间目录上的配额随之
    释放）。删除设了 `trash` 的那个目录本身（`rm -r`）第一次会报 `ENOTEMPTY`（删的过程中回收站又被建了出来）：先
    `wmfs unset <目录> trash` 再删。别人的子目录是 0700，所以回收站里还有别人的文件时，非 root 用户删不掉这棵树（`rm -r` 报
    `EACCES`），要等那些文件到期或由 root 删。
  - **ttl**（`ttl=<时长>`）：子树里 mtime 早于"现在减去时长"的文件由后台任务 ttl 删掉（每分钟一轮，`wmfs task run ttl` 马上来一轮；`trash`
    生效时进回收站），changelog 的 `Unlink` 带 `reason=ttl`。
  - **审计标记**（`audit=on`）：之后这棵子树里的修改（命名空间、setattr、xattr、写入长度与属性变更）在 changelog 里带 `audited: true`，被拒绝的
    修改也记一条（`result` 是错误码）；第一次启用时建 `audit-log` 游标，从此 changelog 按它保留（最多 7 天 / 1000 万条）。把审计记录写进文件
    的 audit-log 在 M14 的 `wmfs mgr` 里；在那之前 `wmfs status` 与 `/api/v1/health` 显示"审计消费者落后 N 条"。
- **改集群图时写会停顿一下（M13 起实测）**：会改集群图的操作（`wmfs set`/`unset` 的 `qos`、`wmfs class create/update/delete`、
  `wmfs cluster set`、`wmfs key` 等）之后约 1 s 内，正在写的文件偶尔有一次写停顿约 1 s（本机实测 0.7–0.9 s）：每个数据节点换上新集群图的
  那一两毫秒里暂停服务，赶上这一刻的写由链头约 0.5–1 s 之后重发。一个存储类（或一种副本数）的第一个文件，第一次写可能停顿约 1–1.5 s
  （本机实测 0.7–1.5 s：新建的链要先传到各个数据节点）。都不报错，只是慢一下（ADR-0044 第 9 条）。
- 声明无法满足时（例如单节点上 `replicas=3`，或 `stripe=4` 但只有 2 条可用的链）：文件照常创建，但实际副本数 / 条带数较少；**不会静默**：`wmfs init` 与 `wmfs dev up` 的输出、server 启动日志、`wmfs mount` 的输出、`wmfs status` 的第一行、`wmfs get` 的 semantics 行（"replicas:声明3/实际1"）、`wmfs set` 时都会警告，dashboard 显示差距；加入节点后自动补齐（ADR-0016，人类于 2026-10-20 批准"照常创建、到处警告"）。
- 集群里每个节点必须启用同一组会影响策略的插件（授权、配额、QoS、放置、变换、后台任务等）。插件配置与集群清单不一致的节点会**退出**并列出差异，而不是带着少一条规则的配置继续服务。M8 起：不一致的节点以退出码 3 退出、日志列出差异与修法；`wmfs join` 时插件配置不同直接被拒绝（退出码 3）；用 `wmfs cluster plugins add|remove`
  改了清单之后各节点都会退出，要用新配置重启全部节点（M9 起：只做数据的节点这时多半拿不到新的集群图——元数据节点都不一致、没有就绪的
  leader——它不退出，但续不了租约、自我隔离，不服务读写；重启全部节点时一并按新配置重启，开发集群用 `wmfs dev restart-all`）；清单里的某个插件再也装不上时，在**全部**元数据节点上（用同一份插件配置）都用
  `wmfs server --data-dir D --adopt-local-plugins` 启动，当选的节点把清单改成本地的，之后去掉这个参数重启（ADR-0039）。

## 8. 安全边界（ADR-0009）

- 服务端强制授权：每个元数据请求都经过权限检查（POSIX 权限、ACL、路径限制）；数据请求凭元数据签发的、带过期时间的签名令牌。
- 客户端机器凭共享密钥（challenge-response，密钥不在网上传输）证明身份；**它声明的 uid/gid 只在该密钥允许的 uid 范围内被相信**，`root_squash` 把 root 映射为 nobody（类似 NFS AUTH_SYS + 主机密钥）。被攻破的客户端主机可以冒充其 uid 范围内的任何用户；它还可以不经路径查找、直接按 inode 号打开文件（与 NFS 的文件句柄相同），这时只检查文件自己的权限位，上级目录（例如 0700 的家目录、别人的回收站子目录）挡不住它（经挂载点的正常访问照常逐级检查；路径限制按文件所在的祖先目录判定，不受影响）。客户端密钥不能冒充服务端（握手时核对角色）。
- 路径限制（path-caps）可以把一把密钥限制在若干子树内（M10：`wmfs key create <名字> --path /proj [--path-ro /shared]`）：子树之外一律 `EACCES`（只读子树里的写是 `EROFS`），子树的上级目录只能查名字、取属性（用来走进子树），不能列出也不能修改；管理 API 按路径的查询（`wmfs get/usage/status`）同样只能查这些子树。限制跟着目录走（目录被 `mv` 之后仍然有效）。
- 密钥可以随时撤销（`wmfs key revoke`）：用它签名的管理请求立即被拒绝；它的会话被驱逐、不能再开新会话；各节点拿到新的集群图之后关闭用它建立的连接（通常 1 秒内），重连时握手被拒。最后一把有效的 admin 密钥不能撤销。新建密钥的文件内容只在创建时给一次（服务端不保存密钥）。
- 调试键空间（`wmfs debug kv`：元数据库里单独的一块调试区域，不碰文件系统的数据）只接受 admin key，且服务端 node.toml 里打开 `debug_ops` 才可用（`wmfs dev` 打开，`wmfs init` 默认关闭）。
- 管理 API（HTTP）：`/metrics` 与 `/api/v1/health` 不需要认证（只含指标与节点地址）；其余接口都要带签名，写操作只接受 admin key。故障注入接口（`/api/v1/failpoints`）只给测试用，只在 node.toml 里写了 `failpoints_api = true` 时存在（`wmfs dev` 默认打开，`wmfs init` 默认关闭）。
- **首发不加密网络流量（没有 TLS）**：只在可信网络中使用。管理 API 的写请求带签名与时间戳，**5 分钟之内被截获的请求可以被原样重放**，超过 5 分钟不行。
- 管理端口（HTTP）只应对可信网络开放：同一网络里的恶意程序可以用不发完的请求占住它的处理线程，让管理命令变慢或无响应（不会让节点崩溃，也绕不过签名；数据读写走另一个端口，不受影响）。首发接受这一限制（ADR-0030）。
- RDMA 下客户端永远拿不到服务端内存的访问钥匙；服务端之间互相信任（服务端之间的请求会带上发起方的钥匙）。服务端一侧的 RDMA 连接不开放远程读写，所以客户端即使猜到了地址与钥匙也读写不了服务端内存（由网卡保证；M2 起）。**rdma 传输未在本机验证**（本机没有可用的 RDMA 链路，见第 10 节）。
- 数据落盘加密（`encrypt=tenant:<名字>`，AES-256-GCM，每块随机 nonce；M11 起：先 `wmfs datakey create <名字>` 建数据密钥，密钥由集群主密钥派生的密钥包裹后存在元数据里，数据节点只在内存里持有解开的密钥，管理 API 里看不到密钥本身）只加密 chunk 数据；开启加密的目录里，已有的小文件在后台转换时也从元数据库转进加密的 chunk；开启加密的目录里新文件不再内联到元数据库；开启加密**之前**写入的内容，以及开启后、转换完成前往已有文件里新写的内容，在后台转换完成前仍是明文（一直写打开的文件不会被转换，第 4 节）；元数据库的空闲页里也可能残留旧明文，直到被覆盖。

## 9. 首发不支持（汇总）

纠删码（`ec`，二期）；快照（`snapshot`，二期——chunk 版本已从第一天按快照需要设计）；NFS / SMB / S3 / ublk 网关（二期插件）；内核客户端与 LD_PRELOAD 拦截库（客户端库与协议已留出复用接口）；跨地域复制；磁带 / HSM；WASM 用户策略（二期，策略求值点已预留，`wasm:` 开头的属性值会被拒绝）；跨节点共享可写 mmap；FUSE passthrough 与 io_uring；cgroup io / NVMe WRR / NVM Sets / FDP 隔离；跨节点协调的 QoS（dmClock）与元数据 QoS；元数据 follower 读；审计 open/read（`audit` 只记录修改类操作）；动态库插件中除授权以外的钩子（ADR-0012，待人类确认）。设置这些功能对应的属性会得到明确错误（`EOPNOTSUPP`"二期功能"），不会被静默接受。

## 10. 承诺的部署组合与本机验证范围

- **只承诺三个 profile 通过全套测试**（理念文档第 9 章）：`minimal`（单节点、TCP、不启用配额）、`hpc-rdma`（3 节点、RDMA、配额、QoS）、`nas-safe`（3 节点、replicas=3、回收站、审计）。**其他插件组合尽力而为**：能用，但没有经过全套测试。
- `hpc-rdma` 在没有真实 RDMA 设备的环境里标为**未验证**（本机只能用 Soft-RoCE 做功能测试；没有 Soft-RoCE 时整套显示 SKIP，发布说明不得声称支持）。本机按人类决定（2026-10-20）不做 RDMA 实机测试，因此 RDMA 在本机属于"未验证"。
- 本机只有一块 NVMe 系统盘，所有"节点"共享它：隔离承诺永远显示 shared，性能数字不代表多机部署；"RDMA 路径不低于 BeeGFS 的 80%"无法在本机验证（ADR-0015）。
- "多节点"是同一台机器上的多个进程：能验证协议与故障处理逻辑，但不是真正的机器级容错。
- 真实设备上的**掉电**持久性（fdatasync 与目录 fsync 的顺序是否在 ext4/XFS 上真的够）本机无法验证：测试用模拟掉电的存储后端检查"该 fsync 的地方都 fsync 了"（元数据从 M3 起、chunk 存储从 M5 起），真实设备上的验证需要有 root 的 dm-log-writes 或 LazyFS 环境补做（ADR-0015）。
- 本机根分区是 ext4（推荐生产用 XFS，ADR-0008）。
