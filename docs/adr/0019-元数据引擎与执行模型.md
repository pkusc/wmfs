# ADR-0019 元数据引擎与执行模型：raft-rs + 单 redb 文件、单飞批次写集复制、expect_version、Safe ReadIndex

- 状态：accepted（人类于 2026-10-20 批准）
- 日期：2026-10-20
- 性质：契约层首次定义（理念文档第 3 章"复制、成员、选举、fencing"的元数据 Raft，"事务与锁原语"的元数据事务；第 7 章 [默认]"内嵌 KV + Raft（3 副本），引擎走 MetaEngine trait"）
- 是否触及契约层：**是**
- 批准类别：**需批准**；确认批次 0（B 栏：技术契约）
- 相关章节：design.md 3.2.6、3.2.9、3.4.1、3.5.1、3.5.2、附录 A

## 背景

最初的想法是：leader 串行执行 + 写集复制 + 多提案流水线 + LeaseBased 读；状态机用内存 BTreeMap + 快照文件。评审核实：流水线在"同 term 内单个提案被丢弃"时会提交基于丢失提案的写集；raft-rs 0.7 的 LeaseBased 不检查任何时间，旧 leader 有约一个选举超时的旧读窗口；内存状态机做快照会阻塞 apply；用"空日志 + 相同配置"引导时 joiner 学不到 voter；LightReady 的 commit 只放内存会导致单节点重启 fatal。另外 `raft::util::limit_size` 总会保留第一条条目：一个超过 1 MiB 的批次会生成超过帧 body 上限的 MsgAppend，连接被断开、leader 永远拿不到多数派确认。

## 决定

1. **存储**：一个 `meta.redb` 同时装 raft 日志、硬状态与状态机 KV；应用写集与"已应用索引"同事务；**任何写入 applied 的事务都同时写入 commit ≥ applied 的硬状态**（两个写事务都写）。raft 线程与执行器线程上的 redb 错误一律"写日志 + abort"（fail-stop）。
2. **执行**：leader 上单线程执行器，**同一时刻 raft 里只有一个批次**；执行器"边取边执行"，一批 ≤ 256 个操作且**写集实际编码字节 ≥ 768 KiB 就结束本批**；独占操作与生成了新链的操作必须是本批最后一个；闭包只做点查（没有 scan）；每个带 seq 的请求的结果（成功或 POSIX 错误，含锁冲突的 `EAGAIN`）都写进去重表，所以错误回复也在提交后才发出；follower 只按顺序应用 KvOp。**没有服务端锁等待队列**（F_SETLKW 由客户端轮询，ADR-0028）。
3. **安全网**：写集带 `expect_version`，每个副本 apply 时与 `state_version` 比较，不等整批作废；提议前检查"仍是同一任期且已就绪的 leader"，否则不提议（降级的 follower 会把提案转发给新 leader）。"就绪"还要求本节点插件清单与集群清单一致（ADR-0025）。
4. **raft 参数**：`max_size_per_msg = 512 KiB`；RaftMsg 的 protobuf 放在帧的 bulk 里（上限 16 MiB），所以即使单条条目约 1.2 MiB 也能发出。回归测试：3 节点提交 900 KiB 写集。
5. **读**：批量 ReadIndex（`ReadOnlyOption::Safe`），leader 就绪后才发、500 ms 重发、2 s 回 RETRY；**否决 LeaseBased**；follower 不服务读。
6. **快照**：从 redb 的 MVCC 读事务现场导出（pin 一个读事务；pin 表是 `Arc<Mutex<…>>`，snap-serve 线程共享），数据经 `SnapshotFetch` 带外流式传输，raft 消息里只放描述符；follower 下载校验后才 step。
7. **成员**：`wmfs init` 写 index = 1 的快照状态引导（同 raft-rs `five_mem_node`）；joiner 空存储启动、先装快照，用 `Joined` 回复里的集群图找到 leader；learner 追上后用一个多变更 ConfChangeV2 一步提升到 3 voter；只提议 V2；leave-joint 依赖 raft-rs 自动退出 + Ready 循环之外的兜底。
8. **集群运行参数**（租约时长等）存在复制状态里，全集群一致。

## 备选方案

- 多提案流水线 + 跨批 overlay：吞吐更高，但正确性规则复杂且已被证明有漏洞。推迟；`expect_version` 已为它准备好基础。
- 内存 BTreeMap 状态机 + 快照文件：快照停顿、内存受命名空间规模限制。否决。
- LeaseBased 读：不安全。否决；将来要做租约读必须自己实现带时钟的租约并写 ADR。
- 执行前按"估算写集"限制批次大小：闭包执行前无法知道写集大小，估算不成立。否决。
- 把帧 body 上限对 RaftMsg 放宽：传输层要懂消息语义。否决（统一"大块字节走 bulk"更简单）。

## 后果

吞吐上限约"每次 fsync（本机 3–6 ms）一批、每批 ≤ 256 个操作 / 768 KiB"，对 1–64 节点的小集群足够；元数据写延迟 ≥ 一次 fsync。
