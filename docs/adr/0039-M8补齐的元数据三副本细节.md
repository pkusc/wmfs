# ADR-0039 M8 补齐的元数据三副本细节

- 状态：accepted（主管于 2026-10-24 按 design.md 开头的例外条款决定：都是规格漏写的技术细节、已批准机制的落实，或文档里一处做不到的运维步骤的更正，不增删功能）
- 日期：2026-10-24
- 性质：ADR-0035 第 11 条的落实（uninline 的 fencing，改了 ADR-0034 第 3 条第 2 步的写入位置）；契约层补齐（快照文件格式、changelog 的 `extra` 键、新的管理 API 端点与 JSON）；几处内部取值；3.7.2 第 5 条逃生口步骤的更正
- 是否触及契约层：**是**（`tests/golden/snapshot.golden`、`api/src/types/cluster/tests.rs` 的 JSON 金样，只增）
- 相关章节：design.md 3.3.1、3.3.4、3.4.1.2–3.4.1.9、3.4.3、3.7.2、3.10、7.1、7.2、8.4、9.2；semantics.md 第 7 节；ADR-0025、ADR-0029、ADR-0034、ADR-0035、ADR-0038

## 背景

M8 实现元数据三副本（join、learner、joint 变更、快照、raft 发送线程、跟随 leader、集群插件清单、节点管理）时，实现者与审查修复遇到下面这些规格没写死的地方，按最小方案做了、加了金样或测试，并上报确认。每一条在 design.md 对应位置都有"实现注记（M8）"。

## 决定

1. **uninline 的数据面 fencing**（ADR-0035 第 11 条，M8 已解决）：
   - 做法与 3.10 迁移原语第 2–6 步是同一个模式（`core/src/meta/uninline.rs` 的文件头）：
     1. 每次尝试先在执行器里提交一个意图：`max_epoch += 1`、`pending_epoch = max_epoch`（CAS：change_id 仍是 c、仍是 inline）。
     2. 把 INLINE 内容写进这个新 epoch 的 chunk 0，并 `SyncChunks`。
     3. CAS 切换：change_id 仍是 c、`pending_epoch` 仍是自己的 → `layout.epoch = pending_epoch`、清 `pending_epoch`、清 F_INLINE 与 INLINE。
   - 别人留下的 `pending_epoch ≠ 0`（旧 leader 没做完的、崩溃留下的）不复用，记为垃圾（GC 记录）。所以旧 leader 迟到的写只会落进作废的 epoch，没人读。
   - 这改了 ADR-0034 第 3 条第 2 步"按文件当前的 layout（同一个 epoch）写"。对外行为不变：客户端用回复里的新 layout，epoch_seen 规则（ADR-0035 第 9 条）照旧。
   - 内容为空（新建之后第一次写大，最常见）时没有东西要搬：不提意图、不碰数据面、epoch 不变，所以新建的大文件仍是 epoch 1。这种情况旧 leader 也什么都不写，没有要挡的。
   - 代价：非空内容的 uninline 每次多一次提交。
   - 意图提交之后、切换之前文件被删掉时，留下的最多 64 KiB 的 chunk 不在 GC 记录里，由 M11 数据节点的本地孤儿扫描清理。
   - 新 fail point `meta.uninline.before_write`。回归用例 `tests/it/failpoint_uninline_fence.rs` 已验证：M5 的写法会失败。
2. **join**（3.4.3）：
   - 新节点以空的 raft 状态启动，先把 `Joined` 集群图里的 NodeRecV1、KEYMETA 与 GLOBAL 的 cluster/settings/features/plugins/map_epoch 预写进 kv：建连认证、插件比对在装快照之前就要用。集群的初始状态不在日志里（init 直接写 index 1），所以新节点一定先装快照，装的时候整张表被替换。
   - NodeRecV1.addrs 取 node.toml 的监听地址（与 init 相同）。`wmfs join` 新增 `--disable 插件` 参数。
   - join 是 exclusive 批次（3.4.1.4 规则 5：改节点记录的内部操作都是，包括 `set_roles` 与 drain/remove/promote 端点）。
   - join 幂等，以便结果不确定时重试：地址、管理地址、host_id、machine_id、hostname、target 路径都相同，且 target 的 boot_id 全为 0（从没启动过）时，当成重试，回原来的 `Joined`、什么也不写；其余撞地址的情况照旧 `EEXIST`。
3. **快照**（3.4.1.7，金样 `tests/golden/snapshot.golden`）：
   - 文件格式：整数一律小端，每条记录的 crc32c 覆盖 klen‖vlen‖key‖value（`wmfs debug meta-hash` 用同一套记录编码）；先写 `.snap.tmp` 再改名；权限 0600（快照是整张 kv 的副本，含 inline 内容、xattr、KEYMETA、DATAKEY）。
   - 残留文件：节点启动时删掉 `snap-recv-*` 的全部残留（含 `.tmp`），之后 snap-recv 在下一次下载开始时删掉 10 分钟以前的。
   - 复用已有的 pin 时，另要求接收方在 pin 的 ConfState 里（raft-rs 会拒收 ConfState 里没有自己的快照）。
   - 本地查不到对端地址时，依次问认识的节点要集群图（最多每 5 s 一次，遇到 follower 按 `leader_hint` 再问）。
   - 快照流的接收窗口是 16 帧（有背压）。
4. **跟随 leader**（3.3.1、7.1、7.2）：
   - 回 `NOT_LEADER` 时一律填 `leader_hint`。客户端与 join 连续跟随 `leader_hint` 最多 3 跳，之后正常退避；hint 指的地址连不上就回到种子。
   - 管理 API 的客户端收到 503 not_leader 也换下一个地址；`wmfs dev leader` 只相信自称就绪 leader 的节点。
   - 只做数据的节点（不是 raft 成员）按 raft 的 leader、上次成功的地址或 `leader_hint`、认识的节点（轮流试）找 leader。
   - 管理 API 读写途中遇到 `NOT_LEADER`，一律按 ADR-0038 第 2 条回 409（带新 leader 的管理地址）或 503。changelog 长轮询的等待者在本节点失去 leader、新角色发布之后立即返回。
5. **成员与换 leader**（3.4.1.9）：
   - "追上" = `matched > 0 && matched + 1000 ≥ commit`。plan、选接替者、`GET /api/v1/cluster` 的 `caught_up` 共用这一个判断（`EngineStatus::caught_up`）。审查发现的阻断问题：没有 `matched > 0` 时，新集群（commit < 1000）会提升一个什么都没收到的 learner。
   - 选接替 leader 的人（drain、移除 leader 自己、SIGTERM 让位共用）只选三个条件都满足的 voter：没在 drain 或移除、最近 10 个 tick 内来过消息、已追上。没有就不让位。
   - `wmfs dev up --nodes N` 等到成员到位：N ≥ 3 时 3 个 voter，N = 2 时 1 voter + learner；不在 joint 中；都已追上。
6. **集群插件清单的逃生口（3.7.2 第 5 条的更正）**：
   - 原文"在**一个**元数据节点上用 `--adopt-local-plugins` 启动"在多节点集群里做不到。没带这个参数的元数据节点一启动就因清单不一致以退出码 3 退出，只靠一个节点凑不够多数派，选不出 leader。审查已复现。
   - 改为：在**全部**元数据节点上（用同一份插件配置）都带 `--adopt-local-plugins` 启动；当选的节点把清单改成本地的之后，去掉这个参数重启。design 3.7.2 第 5 条、semantics.md 第 7 节已改；`plugins::FIX` 的文案在 M9 第一步改。
   - **M9 第一步补一条安全规则**（约 5 行）：这个参数只管到本节点的本地清单第一次与已应用的集群清单一致为止，之后照常比对。否则带着参数、但配置不同的两个节点，会在换 leader 时把清单来回改成各自的，而且都不退出——正是清单比对要防的"带着少一条规则的配置继续服务"。有了这条规则，配置与改好的清单不同的节点照常以退出码 3 退出。
   - 测试：两个节点带参数但配置不同时，有一个以退出码 3 退出；三个节点带参数且配置相同时，收敛后都照常运行。
7. **changelog 的 `extra`**（ADR-0029 的补充）：`NodeJoin`/`NodeDrain`/`NodeRemove`/`NodePromote` = `node`（节点号；`NodeJoin` 的 `name` 是 hostname）；`PluginListChange`/`PluginListReset` = `old`/`new`（逗号分隔的清单）。
8. **新的管理 API 端点与 JSON**（7.1，金样 `api/src/types/cluster/tests.rs`）：
   - `GET /api/v1/cluster`（`ClusterReply`/`NodeInfo`；`member` 是节点在 raft 里的实际身份，`member_wanted` 是 NodeRecV1 指定的身份，不与 health 的 `meta_role` 同名）。
   - `POST /api/v1/nodes/<id>/{drain,remove,promote}`（`NodeOpReply`）。
   - `GET|POST /api/v1/cluster/plugins`（`PluginsReply`/`PluginsReq`）。
   - `GET /api/v1/debug/meta-hash`（节点本地、要认证，`MetaHashReply`）。`wmfs debug meta-hash` 先问 leader 谁是元数据成员，只比成员，非成员列在 `not_members`。
9. **选举期间的管理命令**：一次性的管理命令在选举的 1–2 s 内可能失败（全部地址连不上、503，或 409 指向刚被杀的 leader），重试即可；`wmfs changelog tail -f` 会自己等（最多 60 s）。
   - 不给所有管理命令默认加等待：`wmfs dev` 的健康检查与等待轮询依赖它立即失败。
   - semantics.md 第 7 节 M8 一段改成如实的说法："选出新 leader 之后自动换到它"。
10. **新的集群警告**（3.4.1.9）：
    - 元数据没有高可用：有 ≥ 2 个元数据节点、但不到 3 个 voter。
    - 故障域重叠：同一个 machine_id 上有多个节点。
    - "数据的链式复制在 M9 实现，现在实际只有 1 副本"：这是分阶段的说明，M9 删掉。
11. **内部取值**（不进线上格式与磁盘格式）：
    - raft-send 发送失败后退避 100 ms 起翻倍到 1 s，期间丢掉发给这个对端的消息（MsgSnapshot 除外）。
    - `EngineStatus.active` 的窗口是 10 个 tick。
    - `wmfs dev start` 最多等 30 s 让这个节点追上。
    - 新 fail point：`raft.compact.small`、`snapshot.fetch.midway`。
    - 新指标：`wmfs_raft_msg_sent_total`、`wmfs_raft_snapshot_sent_total`、`wmfs_raft_snapshot_installed_total`。
12. **测试**（9.2）：
    - 同一进程里停掉的节点不能再启动（redb 文件锁），所以重启与追平只在多进程的 `scripts/accept.d/m8.sh` 里测。
    - 3 节点确定性模拟用"读放行时包含之前已确认的写""读到过的写不消失"代替 Wing-Gong 回溯（与 M3 一致）。每个写批次另写一个临时键并删掉上一批的，以覆盖装快照时"先删 kv 表"（规则 M5）。
    - `--release` 下 1000 个种子约 73 s，确认约 2.25 万个写、装约 1,400 个快照。`WMFS_SIM_SEEDS` 控制种子数，普通 `cargo test` 默认跑 100 个。

## 留给后面的

- M9 第一步：
  - 第 6 条的安全规则与 `plugins::FIX` 文案；
  - `wmfs dev restart-all`（3.7.2 第 4 条：用新配置重启全部节点；现在开发环境只能 `wmfs dev down` 再 `wmfs dev up`）。
- M9：
  - 删掉第 10 条的"实际只有 1 副本"警告；
  - join 的新节点现在只登记 TargetRecV1，要补进链；
  - `wmfs node drain` 现在只让出 leader、不再被提升，迁走链在 M9；
  - `call_cb` 还在调用线程上建连，repl 线程用之前改成后台建连；
  - ADR-0038 第 5 条（调小 target 租约的过渡规则）随 target 租约回收一起做。
- M11：uninline 意图之后文件被删掉时留下的 chunk（第 1 条），由数据节点的本地孤儿扫描清理。

## 后果

元数据三副本这一层的取值从 M8 起固定，由金样与测试守住；后面的里程碑只增不改。ADR-0035 第 11 条已解决。ADR-0034 第 3 条第 2 步的写入位置以本 ADR 第 1 条为准。
