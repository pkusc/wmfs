# ADR-0035 M5 补齐的数据路径细节

- 状态：accepted（主管于 2026-10-22 按 design.md 开头的例外条款决定：都是规格漏写的技术细节，不增删功能；第 5 条是已批准格式本来就有的上限，写明而已）
- 日期：2026-10-22
- 性质：契约层补齐（几个拒绝码与回复、`Open.flags` 等常量的数值、cap 的签发规则）与几处实现取值
- 是否触及契约层：**是**（`constants.golden`、`data.golden`、`meta.golden` 已更新，只增）
- 相关章节：design.md 2.2、3.2.3、3.2.5、3.3.4、3.3.5、3.4.2.9、3.5.1、3.10、3.11；ADR-0021、ADR-0023、ADR-0033、ADR-0034

## 背景

M5 实现单节点数据路径（chunk 格式、local-fs、cap、CommitWrite、服务端 uninline、gc）时，实现者与审查修复遇到下面这些规格没写死的地方，按最小方案做了、加了金样或测试，并上报确认。每一条在 design.md 对应位置都有"实现注记（M5）"。

## 决定

1. **拒绝码与回复**（3.3.4、3.3.5）：
   - cap 所属的会话已被驱逐 → `SESSION_EVICTED`；数据节点还没拉到集群图 → `NOT_READY`；其余 cap 不符一律 `BAD_CAP`。
   - `Fallocate` 回 `Entry { attr }`；`GetInline` 对已经不是 inline 的文件回 `STALE_LAYOUT`；`StatFs` 的 `bsize = 4096`、`files = ffree = 2³² − 1`、`namelen = 255`，容量与已用取各 Up target 最近一次心跳之和（leader 内存里）。
   - 截断一个从没写过的 chunk：不建文件，回 `Written { version: 0 }`（它读起来本来就是 0）。
   - `Open.flags` 的访问方式取 Linux open(2) 的数值（`O_RDONLY = 0`、`O_WRONLY = 1`、`O_RDWR = 2`、`O_ACCMODE = 3`）；`CODEC_REPLICA = 1`。钉在 `constants.golden`。
2. **cap 的签发**（3.3.5，ADR-0023）：
   - 只读打开 → 读；只写 → 写；读写 → 读 + 写；新建的文件 → 读 + 写；为写打开已有文件（不带 `O_EXCL` 的 Create、改长度的 SetAttr、Uninline）→ 写，调用者能读时再加读。
   - 后台任务的请求 = cap 带管理权限位，走 QoS 的低优先级队列；管理 cap 只签给后台任务。
   - 服务端 uninline 用 `session = 0` 的写 cap（不属于任何会话）。
   - Open、RenewCap、Uninline 走只读路径，执行器的会话检查覆盖不到它们，所以签 cap 之前先核对会话：会话 Active 且属于这把 key；`session = 0` 只给内部请求与 Server 角色，别人 → `EINVAL`；会话不在 → `SESSION_EVICTED`；别的 key 的会话 → `EACCES`。否则任何客户端都能拿到一张"永不被驱逐"的 cap。
3. **服务端 uninline 的并发**（ADR-0034 的补充）：同一个 inode 同时最多一个、全部加起来最多 `READ_THREADS / 2 = 4` 个，超出回 `BUSY`（客户端退避重试，重试时多半已经不是 inline，直接幂等成功）。原因：落后的那个会在别人 CAS 成功、写了新数据之后再把旧内容盖回 chunk 0；它们又在 meta-read 线程上同步等数据面，而数据节点要经同一组线程拉集群图。数据节点拉到集群图之前每 100 ms 心跳一次。服务端写完 chunk 0 再截断到内容长度（上一次没做完的 uninline 可能留下更长的旧内容）。fail point `meta.uninline.before_commit`。
4. **坏 chunk 的写**（3.2.5 R5，按原文从严）：chunk 已标 Corrupt 时，只有"不保留任何有数据的旧块"的写（整个 chunk 覆盖写、截断到这个 chunk 的开头之前）照常执行并清除标记；其余在单副本上回 `EIO`。头坏到读不出块表的 chunk：只接受整个覆盖写或截断到 0，新版本号取 `incarnation << 40`（旧版本号已经不知道）。
5. **单个文件的最大长度** = `min(chunk_size × 2³², i64::MAX)`（4 MiB 的 chunk 是 16 PiB），超过 → `EFBIG`（改长度的 SetAttr、CommitWrite、Fallocate、客户端算 chunk 号）。这是已批准格式本来就有的上限（chunk 号 `ChunkId.idx` 是 u32、`st_size` 是有符号 64 位），不设限的话偏移会回绕到前面的 chunk、静默毁掉数据。semantics.md "上限"一项已写明。
6. **inline 文件截断到 0 也写 kind 2 GC 记录**：ADR-0034 之后 inline 文件的 epoch 下面也可能有 chunk（uninline 写完 chunk、提交之前崩溃），按 ADR-0034 第 3 条由 gc 按 epoch 清理。代价是小文件每次覆盖写多一条 GC 记录。
7. **容量**：target 已用达到 `min(node.toml 的 capacity, 文件系统大小)` 时写回 `ENOSPC`，截断照常。不认识的 ro_compat 位 → target 只读：写、截断、DeleteEpoch 回 `EROFS`，放置时跳过它。
8. **按 roadmap 留给后面的**：损坏上报 ReportCorrupt 与 DataLossDetected 事件、EveryDataNode 类后台任务、本地游标、`wmfs task`、数据节点的本地孤儿扫描（M11）；读副本的选择 `read_order`、心跳判离线与租约（M8/M9）；mclock 与按用量放置（M13）；`want_quota`（M10）与 `close`（M6）。

## 留给 M6 第一步要修的（已定方案）

9. **按旧的 inline 视图截断**：客户端 A 以为文件还是 inline，跳过 TruncateChunk 直接发 `SetAttr{size: s}`；而文件刚被 uninline（epoch 不变），服务端照样改了长度，chunk 里 s 之后的旧数据没清零，之后把文件扩长就会冒出旧数据。原设计（客户端自己 uninline）也有这个缺口。修法：**`epoch_seen = 0` 表示"我看到的是 inline、没有发 TruncateChunk"**（epoch 从 1 起，0 不会是真的 epoch）；服务端对已经不是 inline 的文件，`epoch_seen` 与当前 epoch 不同（包括 0）→ `STALE_LAYOUT`，客户端重新 Open、按 chunk 截断。去掉现在"`epoch_seen = 0` 就不检查"的行为。服务端约 1 行、客户端约 1 行。
10. **已打开的句柄在权限被去掉之后**（CommitWrite 等按当前权限重查，git、cp 先建 0444 文件再写会在 close 时 `EACCES`）：人类已决定"学 NFS"（ADR-0036），M6 实现。

## 留给 M8 的（M8 必须解决）

11. **换 leader 之后旧 leader 上没做完的 uninline**：第 3 条的互斥只在当前 leader 的内存里。M8 有了多个元数据节点之后，旧 leader 上落后的 uninline 可能在新 leader 上的 uninline 成功、客户端已经写了新数据之后，才把旧内容写进 chunk 0。M8 要给它加数据面的 fencing（例如服务端 cap 带上 leader 的任期，数据节点拒绝旧任期的；或者 uninline 的写带"chunk 版本必须是 v"的条件）。M8 之前只有一个元数据节点，不会发生。**M8 已解决**：意图 + 新 epoch（与 3.10 迁移原语同一个模式），见 ADR-0039 第 1 条。

## 后果

数据路径的这些取值从 M5 起固定，由金样与测试守住；后面的里程碑只增不改。第 9、10 条在 M6 修，第 11 条在 M8 修。
