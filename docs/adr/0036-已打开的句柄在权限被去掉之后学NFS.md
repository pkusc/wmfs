# ADR-0036 已打开的句柄在权限被去掉之后：学 NFS

- 状态：accepted（人类于 2026-10-22 决定："学 NFS"）
- 日期：2026-10-22
- 性质：semantics.md 放松清单新增第 17 条；钩子 ABI 只增（`AuthzOp` 末尾追加一个变体）；线上协议只增（`MetaOp` 末尾追加一个变体）
- 是否触及契约层：**是**（`AuthzOp` 的 C ABI 编号表、`meta.golden`，随 M6 更新）
- 相关章节：design.md 3.3.4、3.5.1、3.7（authz 组合规则）、8.4、8.5、posix-mode 的规则表；semantics.md 3.3；ADR-0009、ADR-0023、ADR-0033 第 7、12 条、ADR-0034、ADR-0035

## 背景

POSIX 只在打开文件时检查权限，打开之后句柄一直可用。很多常用程序依赖这一点：git 存对象、cp 复制只读文件，都是先建一个只读（0444）的文件，再用建文件时拿到的句柄往里写。

wmfs 的打开是无状态的：服务端不记"谁打开了哪个文件"，只签一张有期限的令牌（cap，ADR-0023）。M5 里，"经已打开的句柄"发出的元数据请求（`CommitWrite` 提交长度、`RenewCap` 续期等）都按**当前**权限重新检查，于是上面这些程序会在 close 时报 `EACCES`。可选的做法：① 学 NFS：属主不重查；② 每个请求带上打开时的令牌，服务端认令牌（改 6 种请求的格式，约 100–150 行）。人类选了 ①。

## 决定

1. **新的授权操作 `AuthzOp::Handle { read: bool, write: bool }`**，意思是"经已经打开的句柄读 / 写"，追加在 `AuthzOp` 末尾（C ABI 的编号也追加，只增不改）。下面这些请求改用它：
   - 写：`CommitWrite`、`Fallocate`、`AppendReserve`（M12）、`Uninline`、`RenewCap { write: true }`，以及第 3 条的 `TruncateHandle`；
   - 读：`RenewCap { write: false }`。
2. **posix-mode 的规则**：root → 放行；**文件的属主 → 放行，不看权限位**（与 Linux NFS 服务端的 owner override 相同）；其他人与 `Open { read, write }` 的规则相同（看属组 / 其他人的权限位）。有扩展 ACL 的 inode 照旧弃权（ADR-0033 第 12 条）；M10 的 posix-acl 对 `Handle` 也要先放行属主。M10 的 path-caps 把 `Handle` 当成同样读写的 `Open` 来查：路径限制不因为是属主而放松。
3. **经句柄的 ftruncate**：新请求 `MetaOp::TruncateHandle { ino, size, epoch_seen }`，追加在 `MetaOp` 末尾。它与 `SetAttr { size }` 走同一段代码，只是授权用 `Handle { write: true }`。FUSE 的 setattr 带着写句柄（`FATTR_FH`）改长度时发它，`O_TRUNC` 也走它。按路径的 `truncate` 仍发 `SetAttr`，照常按当前权限检查（POSIX：要有写权限）。
4. **不变的**：打开本身（`Open`、`Create`）照常按当前权限检查。所以属主仍然不能以写方式打开一个没有写权限位的已有文件（与 POSIX 相同）。数据面照旧只认 cap。
5. **semantics.md 放松清单第 17 条**（原文）："已经打开的文件，之后被去掉读写权限（chmod、chown、改 ACL）：**属主**自己的句柄照常可用（与 NFS 相同；git、cp 先建只读文件再往里写也靠这一点）；**其他用户**之前打开的句柄，之后可能报 `EACCES`——写在下一次提交长度（写回、fsync、close）时，读在令牌续期时（打开约 8 分钟之后）。"
6. **体量**：约 50 行（新变体与 posix-mode 规则约 15 行，6 处调用改用新操作，`TruncateHandle` 约 20 行，客户端在 M6 的 FUSE 里一并做）。

## 实现注记（M6，主管 2026-10-23，见 ADR-0037 第 4 条）

- 第 3 条的"`O_TRUNC` 也走它"做不到：内核为 `O_TRUNC` 发的 `SETATTR(size = 0)` 不带句柄，所以发 `SetAttr`（前一步的 Open 刚查过写权限，结果相同）。带写句柄的 ftruncate 照常发 `TruncateHandle`。
- 布局变了之后（别人截断到 0、M11 的迁移）重新取 layout 原来只能用 `Open`（按当前权限），属主的句柄会得到 `ESTALE`。M7 补一个只增的 `MetaOp::ReopenHandle { ino, write }`：`Open` 的经句柄版本，授权用 `Handle`。之后第 5 条"属主自己的句柄照常可用"在布局变化时也成立。

## 备选方案

- ② 请求带上打开时的令牌：完全符合 POSIX，但要改 6 种请求的格式（`CommitWrite`、`RenewCap`、`Fallocate`、`AppendReserve`、`SetAttr`，以及布局变了之后重新 `Open`），约 100–150 行，元数据服务还要多验一种令牌。人类没有选。
- 保持 M5 的做法（一律按当前权限重查）：git、cp 在 close 时报 `EACCES`。否决。
- 只放宽写、不放宽读：属主的读句柄 8 分钟之后会坏，与 NFS 不一致，规则也更难说清。否决。

## 后果

属主的句柄与 NFS 一样不受 chmod 影响；其他用户的句柄可能在提交或续期时失败，已写进 semantics.md。授权插件要认识新的 `Handle` 操作（不认识的插件按组合规则弃权）。M6 实现服务端与 FUSE 两边，测试覆盖：属主建 0444 文件后写入并 close 成功；属主 `fchmod 0444` 之后继续写、ftruncate 成功；其他用户的写句柄在 `chmod o-w` 之后提交报 `EACCES`；按路径 `truncate` 一个属主自己的 0444 文件仍报 `EACCES`。
