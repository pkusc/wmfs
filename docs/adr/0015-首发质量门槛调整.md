# ADR-0015 首发质量门槛与分阶段 profile 测试规则

- 状态：accepted（人类于 2026-10-20 批准）
- 日期：2026-10-20
- 偏离条款：理念文档第 9 章"语义：pjdfstest、xfstests（FUSE 子集）、LTP；性能：fio、IOR/mdtest、IO500、elbencho，基线对比 BeeGFS，RDMA 路径不低于其 80%；正确性：……dm-flakey 模拟坏盘"；10.4"一个功能完成当且仅当……三个 profile 的测试通过"
- 是否触及契约层：否（但改变发布门槛与"完成的定义"）
- 批准类别：**需批准**（A 栏：要你拍板）；确认批次 0（M0 开工前：从 M0 起就按它判断"完成"）
- 相关章节：design.md 9.2、9.3、9.6、9.7；roadmap.md 第 0 节第 4 条、M15；semantics.md 第 10 节

## 背景

本机：单块 NVMe 系统盘、没有可用 RDMA 链路（只能 Soft-RoCE）、没有 BeeGFS、没有 fio/pjdfstest/mdtest/ior、agent 不运行 sudo；xfstests 需要块设备与 mount helper，dm-flakey 需要 root 与 device-mapper。另外，功能是一个个里程碑长出来的：M0–M5 还没有挂载点，nas-safe 需要的回收站、审计、mgr 要到 M12、M14 才有——"每个里程碑都跑三个 profile"在字面上做不到。`kill -9` 不会丢页缓存，fsync 写错了也照样"不丢"，所以真实进程的崩溃测试验证不了掉电持久性。

## 决定

1. **首发门槛** = ① pjdfstest（docker 容器内以 root 挂载客户端运行；失败必须全部落在预期失败清单里）+ ② 每个 profile fsx 10 万次与 fsstress + ③ fio（含 verify）、mdtest/IOR（easy 与 hard 模式）冒烟 + ④ 自研的故障注入、单机多进程集群测试与 Jepsen-lite 线性一致性检查（fail point 模拟分区、时钟偏移、坏盘，代替 iptables 与 dm-flakey）+ ⑤ 三个 profile（`hpc-rdma` 没有 Soft-RoCE 时明确标为"未验证"，发布说明不得声称支持）。
2. **推迟**：xfstests、LTP（除 fsx/fsstress）、dm-flakey、IO500、与 BeeGFS 的性能对比（含"RDMA 不低于 80%"）、elbencho（与 fio、IOR/mdtest 重叠，源码构建要 boost 等一串额外依赖）——在具备真实硬件与 root 的环境里补做。
3. **分阶段 profile 规则**（"完成的定义"按阶段收紧）：M0–M5 只要求单元测试与 fail point 测试；M6 起每个里程碑跑 `minimal`；M9–M11 跑 `nas-safe` 阶段版（3 节点、replicas=3，只设置已有消费者的属性）；M12 起阶段版加上 `trash` 与 `audit` 标记；M14 起跑完整 `nas-safe`；`hpc-rdma` 从 M9 起有 Soft-RoCE 时每次都跑阶段版，没有就 SKIP。
4. **掉电**：raft 模拟与 CRAQ 组件测试使用模拟掉电的存储后端（redb 的 `StorageBackend` 实现、内存版 `TargetStore`：只有 sync 之后才算落盘，崩溃丢弃其余）；真实设备上的掉电持久性（`fdatasync` 与目录 `fsync` 的顺序在 ext4/XFS 上是否真的够）本机无法验证，需要有 root 的 dm-log-writes 或 LazyFS 环境补测，semantics.md 写明。

5. **RDMA**（2026-10-20 人类决定）：本机不做 RDMA 实机测试——不建 Soft-RoCE、不运行 sudo、仓库里不放 Soft-RoCE 脚本。M2 与 `hpc-rdma` 中需要 RDMA 设备的检查在本机一律 SKIP；RDMA 在 semantics.md 与发布说明里标为"未在本机验证"。

## 备选方案

- 坚持原门槛：本机无法满足，首发永远不能发布。否决。
- 每个里程碑都跑三个 profile：早期里程碑没有 profile 需要的功能，规则无法执行。否决。
- 只在 M15 跑 profile：问题发现得太晚。否决。

## 后果

首发不对性能做对比性承诺；性能数字只作参考；每个里程碑的"完成"都有明确、可执行的 profile 要求。
