# ADR-0044 M13 补齐的存储类、QoS 与放置细节

- 状态：accepted（主管于 2026-11-07 按 design.md 开头的例外条款决定）
  - 内容都是规格漏写的技术细节、落实规格已有规则的修补，或对外说明的澄清。
  - 不增删功能；第 8 条把一个首发不做的改进如实写明。
- 日期：2026-11-07
- 性质：
  - 存储类、QoS、放置与分层的补齐；
  - 新的对外取值的确认（只增）；
  - 两个 M13 之前就有的问题的修补（第 10 条）。
- 是否触及契约层：**是**。
  - `NodeHeartbeat` 末尾加一个字段（第 5 条，金样随之更新）；
  - DIRATTR、管理 API、changelog 的新取值（第 12 条，只增）。
- 相关章节：design.md 3.4.2.10、3.8、3.10、3.11、4.5、4.6、6.1–6.3、7.1；semantics.md 第 4、6 节；ADR-0010、ADR-0011、ADR-0016、ADR-0040、ADR-0041、ADR-0042。

## 背景

M13 实现了这些东西：
- 存储类（TOML 定义、`wmfs class create/update/list/show/delete`）；
- 目录的 `qos`、`tier`、`locality`；
- mclock、label-match 完整版、tiering、rebalance、cache-local-nvme；
- 物理盘解析与隔离承诺；
- `read_order` 接入客户端的读。

三路审查共 62 条意见（1 条 blocker、14 条 major），修复后验证两轮：
- 第一轮发现一个 M9 起就有的链管理器问题（第 11 条），已修；
- 第二轮通过。

下面是实现、修复与验证时上报、要主管定的事。

## 决定

### 对外说法的澄清

1. **读哪个副本**：
   - 所有文件的读都先找与客户端同一台主机上的副本，其余按 chunk 分散到各副本。
   - `locality` 不管读，只管新文件放在哪：理念文档 5.2 写的是"放置偏好、新数据"。客户端也拿不到文件的 locality，要加协议字段。
   - semantics.md 第 4 节原来"`locality` 对读的副本选择立即生效"一句改成上面的说法。读本机副本只会更快，正确性由 CRAQ 的重定向保证。
2. **`qos=<存储类名>` 是活的借用**。实现时存的是设置那一刻的数值，改成：
   - DIRATTR 里存类名；QOS 表（`18 dir`）里放那个类此刻的包络，`QosSpecV1` 不变。
   - `wmfs class update` 改了 `[qos]` 时，在同一个 exclusive 批次里重写借用这个类的目录的 QOS 记录。
     - 先在只读阶段扫 DIRATTR，用 `attr_epoch` 做 CAS，变了回 `EBUSY`"请重试"，与 class delete 相同。
     - 于是 6.1"只改 `[qos]` → 数据节点 ≤ 1 s 用上新份额"对借用它的目录同样成立。
   - 被 `qos=` 借用的类不能删（`EBUSY`）；`wmfs get` 显示类名。
3. **显示"份额 + 尾延迟"还要求类声明了 `dedicated = true`**：
   - 没声明独占的类随时可能有别的类建在同一批盘上。
   - semantics.md 第 6 节原文是"只有……才显示"（必要条件），这一条与它一致。
   - design.md 6.3 表的第一行补上这个条件。
4. **`dedicated` 的含义**（6.1"只用打了该标签、且不被其他类使用的 target"有两种读法）。取"占走"：
   - 新建的 dedicated 类拿走打了它的标签的 target，别的类的新文件从此不用它们。
   - 别的类已经建在这些 target 上的链与数据留着，隔离承诺如实算共用（`shared` + `isolation_downgraded`）。
     这些链不会消失，所以要真正独占，**dedicated 类要在它的盘被别的类用上之前建好**：先建类，再加入打了标签的 target。写进 semantics.md 第 6 节与 design 6.1。
   - 会让别的类一个可用 target 也不剩时（例如 `label = "*"`），新建回 `EINVAL`。
   - 另一种读法（只能用别的类都没在用的 target）下，`label = "*"` 的 default 一建好，dedicated 类就永远拿不到盘，所以不取。

### 补做规格已有的规则

5. **类的 p99 延迟超过 `latency_target` → `PolicyViolation`**（design 3.11、6.2 第 4 层，表里写的是"做"）：
   - 数据节点按类统计客户端请求从到达到完成的延迟，取最近 10 s 的 p99；只统计设了 `latency_target` 的类。
   - p99 随心跳报给 leader：`NodeHeartbeat` 末尾加 `class_p99: Vec<(u16, u32)>`（类 id、微秒）。
     - 这是线格式改动。首发前各节点同版本，金样随之更新，与 ADR-0043 第 3 条改握手同理。
   - cluster-mgr 在某个节点上的 p99 连续 10 s 超过目标时写一次 `PolicyViolation`（`kind=latency_target_exceeded`），回落之后再超再写，与 `qos_reservation_unmet` 相同。
   - 样本太少不判，门槛取最小方案，写注记。
   - semantics.md 照旧"只测量与告警，不承诺"。
6. **每个 QoS 队列有自己的排队上限**：
   - 原来数据服务的排队上限（4096）是整个节点共用的。M13 起上限 `l` 会让请求积压在 mclock 里，一个被限速的租户就能占满全部槽位，别的租户也拿到 `BUSY`，打破"每 (租户, 类) 一个三元组"的隔离。
   - 改成每个队列最多 512（= 4096 / 8），超了只对这个队列回 `BUSY`；后台队列同样。总上限不变。
7. **"label hdd 位于 nvme 设备上（测试用途）"的标注**（design 6.3 正文）：
   - target 报的 `phys_devs` 里的设备名以 `nvme` 开头、而类的 label 是 `hdd` 时，`wmfs status` 与 `wmfs class show` 如实标注。
   - 按设备名判断，不另加心跳字段。

### 首发不做、如实写明的

8. **重启之后链头会集中**（审查发现的 prefer-client 问题，实际影响更大）：
   - 重启过的成员按 3.4.2.7 排到链尾，首发不会把链头调回均匀。
   - 3 个节点、`replicas = 3` 的集群轮流重启一遍之后，所有链的链头都在同一个节点上：
     - 写入口集中在这台机器上；
     - 这个类的写只能用到它在这个节点上的份额；
     - `prefer-client` 也找不到以别的节点为链头的链。
   - 处理：
     - semantics.md 第 6 节在"负载不均时总保底可能达不到、总上限偏保守"之后写明这一种；`locality` 一行改成如实的说法。
     - label-match 加一个退路：没有以客户端节点为链头的链时，优先选有一个成员在客户端节点上的链（读走本机副本）。
     - 自动均衡链头（把多当链头的成员按 ADR-0041 第 13 条第一步降级、移到末尾、重同步之后再提升）改动的是链管理，风险大于收益，首发不做，留作二期。
9. **换图时的写停顿**（验证时观察到，收尾时查明）：
   - 现象：大量写入之后集群图 +1，新文件的前几次 `O_DIRECT` 写会卡 1–1.5 s。
   - 要找出原因：
     - 如果是 I5 的正常路径（数据节点在下一次心跳才换上新图，期间回 `FENCED`，客户端退避），就写进 design 与 semantics.md：`wmfs set qos`、`wmfs class update` 等会改集群图的操作可能让写停顿约 1 s。
     - 如果是别的原因：小改就修，否则写进 escalations。
   - 调查结果（M13 收尾）：是规格本来的路径，没有改代码。分两种情况：
     - 集群图变了而链没变：数据节点从续租到换上新图有 0–3 ms，这期间按 I5 回 `FENCED`。
       - 发给链头的写，客户端退避 10 ms 就过去。
       - 转发给后继的写，要等链头的快速重发。chain-timer 每 500 ms 一拍，实际在回复之后 0.5–1 s 才重发，所以这一次写停顿约 0.7–0.9 s。
     - 一个（存储类, 副本数）的第一个文件：新建的链各节点还不认识，回 `STALE_CHAIN`，每一跳等一次快速重发，停顿 0.7–1.5 s。
       上面"大量写入之后"的现象就是这一种，与之前写了多少无关。
     - 已写进 design 3.4.2.6 的注记与 semantics.md 第 7 节。
   - 缩短停顿有两个小改法，首发都不做，留作二期：
     - 把 chain-timer 的拍子从 500 ms 调到 100 ms：要改 design 1.2、3.4.2.6 写明的时序。
     - 心跳先换上新图再续租：实现顺序不再照 I5 原文，也消不掉第二种情况。
     - 理由：停顿只出现在改集群图的管理操作前后与新类的第一个文件上，约 1 s、不报错；收益小于改时序的风险。

### 修补

10. **两个 M13 之前就有的问题**（验证时偶发，复现过）：
    - **新会话刚开就被驱逐**（M10 起）。
      - 原因：驱逐线程的空闲计时 = now − max(本任期最后一次心跳, 就绪时刻)。新会话的记录在 SessionOpen 批次一应用就扫得到，而 `Live::touch` 要等回调才做。leader 就绪已超过一个会话租约时，若驱逐线程正好落在这个空隙里，新会话会被立即驱逐，刚挂载的客户端就可能遇上。
      - 修法：驱逐线程自己记"本任期第一次看到这个 Active 会话的时刻"，没有心跳记录时从它起算；换任期清空。
      - **不能用 `Live::touch`**：它把会话记成"已收到打开文件的全集"，换 leader 之后孤儿 GC 会以为它没打开任何文件。
    - **M1 第 23 条检查偶发失败**：`times(1,return(EIO))` 可能先被节点给自己的 target 心跳用掉，ping 就没有重试。
      - 检查改成看 fail point 的命中计数（证明经 API 设的 fail point 生效），不再要求 ping 有重试。
      - 产品代码不改。
11. **"持续 10 s 无法把转发送达后继"只算下游一直在正常心跳的那段**（M13 验证的修复，design 3.4.2.10 的注记）：
    - 后继回了任何话（确认、NeedFull、错误帧）就清掉"转发不到"的记录；
    - leader 把上报的时长截到"本 leader 一直看到下游以同一个 boot_id 在租约内心跳"的时长。
    - 规格原文"（成员之间分区、但各自心跳正常）"就是这个意思。不改格式与复制规则；真正的成员间分区照旧 10 s 后两步移出。

### 新的对外取值（确认，只增）

12. 以下都按实现确认，金样已加或这次补上：
    - **DIRATTR**：
      - `qos` 存 `r=<n>,w=<n>,l=<n>,bw=<字节>,burst=<时长>`（五项都写）或类名（第 2 条）；
      - `tier` 存 `<from>-><to>:<条件>`，条件接受任何时长单位；
      - `locality` 存 `prefer-client` 或 `any`。
    - **管理 API**：
      - `GET/POST/PUT/DELETE /api/v1/classes`（`ClassInfo`、`ClassQos`、`ClassesReply`、`ClassReply`，POST 带只增的 `?name=`）；`ClassInfo.per_node` 是向下取整的显示值。
      - 节点本地的 `GET /api/v1/qos`（后台队列的键是 null）。
      - `AttrActual.deficit`。
    - **changelog**：
      - `ClassCreate`/`ClassDelete` 带 `{name, id}`，`ClassUpdate` 带 `{name, id, reconcile}`；
      - `PolicyViolation` 的 kind 有 `isolation_downgraded`（`class`、`isolation`）、`qos_reservation_unmet`（ino = qos 的来源目录，`deficit`）、`latency_target_exceeded`（第 5 条）。
    - **CLI**：`wmfs mount --host-id`，`wmfs dev mount --node n` 用它模拟客户端在节点 n 所在的主机上。
    - **存储类 TOML**：
      - 缺省值：label `"*"`、weight 1、priority 按 label（`hdd` → low）、failure_domain `node`、locality `any`；
      - `[redundancy] replica` 必须写，`ec` → `FEATURE_UNSUPPORTED`，不认识的键报错。
    - **存储类的删除**：只能删没用过的类（有链、被目录属性或别的类的 `tier_to` 提到 → `EBUSY`），扫描之后遇到并发的属性修改回 `EBUSY`"请重试"。
    - **qos 插件不执行份额时**（fifo，minimal profile）：带 `[qos]` 份额的类定义回 `EINVAL`；默认装 mclock，被停用时才装 fifo。
    - **cache-local-nvme**：缓存目录 0700、块文件 0600、`.lock` 防止两个挂载共用；已存在却不是 700 或不属于本用户的目录拒绝挂载；docs.md 写明缓存里是明文。
    - **mclock、tiering、rebalance 的细则**（标签、令牌桶、保底欠额的上报门槛、rebalance 的 20% 差距与每次搬一半）：按各自的 docs.md 与 design 的 M13 注记。
13. **行数**：
    - M13 新增约 1,700 行非测试代码，预算 1,350。
    - plugins 的估算下调到实际（首发的插件都已写完；M14 的 audit-log、webhook 在 wmfs-mgr 里）。
    - 修复后 Σmax 若超过 37,000，报告人类；不超过 38,000 就照常做。

## 后果

- `qos=<类名>` 跟着类变；读一律优先本机副本。
- 一个被限速的租户占不满别人的排队位置。
- dedicated 的规则与部署顺序写清楚了。
- 类的 p99 超过目标时有事件；会话不会刚开就被驱逐。
- 重启之后链头集中写进了 semantics.md，链头均衡留作二期。
- 改集群图时写可能停顿约 1 s，如实写进了 semantics.md 第 7 节。
