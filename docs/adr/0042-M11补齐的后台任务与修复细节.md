## 背景

M11 实现了这些东西：
- 后台任务框架（调度、限速、可续跑的游标、暂停与恢复）；
- 协调器（声明 vs 实际，迁移原语）；
- scrub（核对与修复）；
- gc 完整版（去重记录、changelog 修剪、数据节点的本地孤儿扫描、递归计数的在线自检）；
- 5 个变换插件、数据密钥与 `wmfs task`。

之后有三路审查，共 59 条意见。修复 agent 改到一半时 API 断线（M10 也断过一次），之后只修了验证时的 3 个失败。主管另起五个核对 agent 逐条核对：44 条已修好，其余 15 条的处理见下文。核对时顺带发现的问题也一并定下。

## 决定

### 新的对外取值（确认，只增）

1. **`ReportCorrupt{target, chunk}` 的取值**：
   - `target = 0` 表示一个好副本也没有，leader 写 `DataLossDetected`；
   - `target ≠ 0` 表示这个 target 上的副本已修好，leader 写 `ChecksumRepaired`。
   规格只给了这一个消息，用 target 的保留值 0 区分两种结局，不改线格式。
2. **changelog**：
   - 新操作码 `RStatDrift = 108`（ADR-0029 的表里没有）：协调器的在线自检修正了一个目录的递归计数，`extra` 写 bytes/files/dirs 的差值。
   - M11 用到的操作码的 `extra` 键按实现确认：
     - `SwitchLayout`：old_epoch/new_epoch/replicas/compress/encrypt_key；
     - `TaskControl`：kind/action/bw/items；
     - `DataKeyCreate`：id/name/tenant；
     - `ChecksumRepaired`/`DataLossDetected`：chain/epoch/idx/target；
     - "一直写打开、被跳过"的 `PolicyViolation`：skipped_ms 等；
     - `RStatDrift`：见上。
   - 修复时逐项核对金样，缺的补上。
3. **节点任务的本地游标文件** `<data_dir>/run/task-<kind>.cursor`：版本字节 + postcard(`LocalTaskV1 {rec: TaskRecV1, run_seen}`)，金样在 `tests/golden/records.golden`。
4. **管理 API 的 JSON**（7.1）：`TaskInfo` 等任务结构，以及 `GET /api/v1/node` 的 `{node_id, tasks, controlled}`，按实现确认。
   - 7.1 表里这个端点的 target、boot_id、内存池、线程数等字段随 M14 补上，只增字段。
   - `…/set` 的 `bw = 0` 表示"用任务自己的默认值"，不是"不限"；design.md 的注记照代码改。

### 回收与修复

5. **废弃 epoch 的回收按来源分两种**（审查 #31；semantics.md 第 7 节）。M11 实现时让所有换下来的旧 epoch 都等"没人打开着这个文件"才删，这会让一直开着日志文件的程序在 copytruncate 式轮转之后永远不释放旧数据。现在分开处理：
   - **截断到 0、覆盖写**（`O_TRUNC`）换下来的旧数据，以及作废的 uninline/迁移意图，照 M10 的口径：宽限期（`epoch_gc_grace`，默认 60 s）过了就删，GC 记录照旧是 kind 2。之后拿着旧布局的读者按 C5 看到截断，cto 允许。
   - **后台转换（迁移）换下来的旧布局**：内容与新布局相同。新的 GC 记录 kind 3（`GC_MOVED`）表示它，除了宽限期，还要等没有会话打开着这个文件、距写记录超过 2 个心跳周期。roadmap M11 的验收"GC 在文件仍被打开时不删除旧 epoch"指的就是这种：拿着旧布局的读者照样读得到，关了才删。
   - 删除后仍打开的文件（kind 1）不变。
   - 数据节点的本地孤儿扫描把 kind 2、3 都当成"leader 的 gc 还管着"，不碰它们。
6. **头读不出时的写**（审查 #26 的修法残留的漏洞）。M11 的修复让"头读不出、链上没有别的 Serving 成员可以先修复"的整块覆盖写猜一个版本号 `((inc+1)<<40)-1`。同一个 incarnation 里第二次碰上时，这个号比后继手里的小，后继按"已提交 ≥ V"回重复确认、不落盘，已确认的写就丢了。改成：
   - 有别的 Serving 成员 → 先修复再写（照旧）；
   - 链上只有自己（没有后继）→ 照常写，版本号按 `max(1, inc<<40)`，没有人会与它冲突；
   - 有后继但都不是 Serving → 回 `EIO`，与 M5 相同，诚实报错，不猜版本号。
7. **读路径发现坏块，马上排队修复**（3.2.5 R5，impl 的 escalation）。与写路径用同一个修复线程，客户端照旧换下一个副本读。原来要等 scrub 的下一轮，默认 24 h。修好或修不了照第 1 条上报。
8. **scrub 与 gc-local 缓存的列表**：调度器开始新的一轮时（包括 `wmfs task run` 让这一轮从头再来），插件要丢掉缓存的列表重新列，否则漏掉之后才写的 chunk。
9. **列举的代价**（审查 #30）。下面三处不改，把代价写进 design.md 3.2.5、4.12 的注记：
   - 修复时每修一个 chunk 发一次 `ListChunks(limit 1)`：修复本来就少。
   - 第 2 段与 L 比对按 1,000 一页：每页在 L 上整链列一次，一轮是 O(N²/1000)。一条链 10 万个 chunk（默认 4 MiB 的 chunk 是 400 GiB）时一天约 20 s；100 万个时约半小时。
   - local-fs 的列举不从游标处开始。
   首发的目标是小集群，单条链超过约 100 万个 chunk 时再按游标分段列。

### 协调器与显示

10. **放弃旧 leader 留下的迁移意图**（审查 #40，3.10 第 6 步）：文件的声明已经不再不同，但 `pending_epoch ≠ 0`、又不是本进程在迁移它 → 也走迁移原语的放弃路径（清 `pending_epoch`、写 GC 记录）。
    - 旧意图的 L′ 的链没有记下来，GC 记录带的是当前布局的链。L′ 上写了一半的数据由 gc-local 在记录删掉、过了 min_age 之后清理。写进注记。
11. **加密改回不加密之后的 inline 阈值**：迁移的意图用声明的 inline 阈值，而不是沿用旧布局里的 0。否则解密后的文件永远 `inline_max = 0`，status 的 inline 一行一直不一致。
12. **`wmfs dev wait task-idle` 与 `wmfs task list` 连不上某个节点时**：
    - task-idle 不把连不上的节点当成空闲，一直等到超时，超时信息写出等的是哪个节点；
    - task list 把这个节点显示成连不上。
    - 只做数据的节点（`controlled = false`）收不到 `wmfs task run/pause/set`，一直按默认值跑；task-idle 对它们只等这一轮做完、积压为 0。semantics.md 与 `wmfs task run` 的帮助文字写明这一点。
13. **status 的 quota 一行**：实际 = 管着这个目录的各个配额此刻的用量与上限；超软限（含宽限已过）或超硬限算不一致。semantics.md 第 1 节里"quota 的实际随各自的里程碑加入"的说法去掉 quota。
14. **一直丢着数据的文件挡住协调器的那一项**：有 `DataLossDetected` 的文件迁移不了，那一项一直留在积压里。这一条写进 design.md 3.10、4.12 与 semantics.md 第 7 节。
15. 其余审查意见与核对时的发现（改名、注释与代码不一致、重复代码、缺的测试、行数估算）按建议改，见 design.md 各处的"实现注记（M11 审查）"。

### 修复时补定的（主管，2026-11-06）

16. **再确认几项只增的取值**（修复 agent 列出、ADR 前文没点名的）：
    - DIRATTR 里 `compress` 存 `none`/`lz4`/`zstd:<级别>`（只写 `zstd` 存成 `zstd:3`），`encrypt` 存 `none` 或数据密钥的十进制 id，不存名字。金样在 `tests/it/bg_reconcile.rs`。
    - `DATAKEY.wrapped` 的附加数据是 `WMFS-DKEY1‖cluster_id‖名字`，K_wrap 在加密插件里用 key_id 0。
    - `CheckEpochs` 一次最多 1,000 项，多了回 `EINVAL`（常量金样 `CHECK_EPOCHS_MAX`）。
    - 节点任务把集群级 `TaskRecV1.pass` 当"运行请求号"用，配本地游标里的 `run_seen`。
    - 协调器的积压按目录数计：`TaskInfo.progress` 为 0，没有 `wmfs_task_progress_ratio{task="reconciler"}`（`backlog_in_dirs`）。刚当上 leader、调度器还没跑过、按库里的记录回答时也是 0（主管修复时补上：以前这时回 1.0）。
17. **全部副本都坏、头又读不出**（第 6 条的一角）：
    - 这个 chunk 的整块覆盖写与截断都回 `EIO`，包括把文件截短到它之前时发的 `TruncateChunk(0)`。
    - 只有截断到 0（或 `O_TRUNC`，换 epoch）或删掉文件能恢复。
    - semantics.md 第 7 节"校验"一句补上多副本的这一种情况。
18. **读路径的修复排队**：已标坏、还没判定丢失的 chunk，每读到一次就再排一次（队列 256，满了丢弃）。单副本的链第一次读到坏块就报 `DataLossDetected`（修不了），之后不再排队。
19. **`wmfs task list --json` 不含连不上的节点**（JSON 仍是 `TasksReply`），只在文字输出里列"连不上"。`wmfs dev wait task-idle` 对连不上的节点另有判定（第 12 条），脚本用它就够了。不加字段。

## 后果

- 截断与覆盖写的旧数据照 M10 的口径回收；只有后台转换换下来的旧布局等文件关闭。copytruncate 式的日志轮转不再泄漏空间。
- 头读不出又没有可修复来源时，写报 `EIO`，不会再"确认了、却没写进后继"。
- 读到坏块之后马上修，不必等一天。
