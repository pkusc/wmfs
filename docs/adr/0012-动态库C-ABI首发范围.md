# ADR-0012 动态库稳定 C ABI 首发只覆盖 authz

- 状态：accepted（人类于 2026-10-20 批准）
- 日期：2026-10-20
- 偏离条款：理念文档 4.2"进程内（热路径）……编译期特性开关 + 动态库（稳定 C ABI；Rust 实现通过 C 壳导出）"；第 3 章 [固定]"钩子管线与插件 ABI"
- 是否触及契约层：**是**
- 批准类别：**需批准**（A 栏：要你拍板）；确认批次 5（M14 开工前）
- 相关章节：design.md 3.7.2、3.7.5、3.7.6

## 背景

热路径钩子（transport、chunk_store、transform 等）的 Rust trait 参数里有 `Buf` 所有权、trait 对象与回调；把它们全部稳定成 C ABI 工作量大、风险高（所有权跨 FFI、panic 跨边界）。理念文档要求热路径钩子可以走动态库；做好一个钩子就足以证明"冻结 ABI、版本列表、不兼容即拒绝"这套规则成立。压缩类 transform 的动态库会连带 chunk 头的 feature 位、集群级 feature 启用、各节点加载一致性与属性校验规则，是"不要过度工程化"下最该推迟的部分。

## 决定（推荐）

1. 首发全部内置插件**静态注册**（cargo feature；注册表在 `cli/src/registry.rs`，core 不知道有哪些插件）。
2. 动态库 C ABI v1（`core/include/wmfs_plugin.h`）**只覆盖 authz**（扁平结构进、allow/deny/abstain 出，不碰 `Buf` 所有权）。chunk 头 incompat bit2、`compress_alg` 128..=255、feature 名 `chunk.dyn_transform`、协议 feature bit4 都**只保留、不实现**。
3. ABI 规则：v1 结构与符号冻结；新能力 = 新版本号 + 新结构 + `_v2` 符号；core 列出支持的版本（首发 `[1]`），不在列表里一律拒绝加载、不尝试适配；Rust 写的动态插件用 `#[unsafe(no_mangle)] pub extern "C" fn` 导出并 `catch_unwind`（panic 视为 deny）；库在进程生命周期内保持加载。
4. **配置了却加载失败（ABI 不符、初始化失败）的动态库 → server 拒绝启动**并写明原因：跳过一个授权插件等于静默少一条授权规则（原则 7）。
5. 动态库插件和静态插件一样进入集群插件清单（ADR-0025）：所有节点必须加载同名插件，少装的节点退出。

## 备选方案

- **再加压缩类 transform**（原方案）：约 +150 行，还需要 `wmfs feature enable chunk.dyn_transform`、`compress=dyn:<名>` 属性、"所有节点都已加载"才允许设置的规则、`examples/dylib-rle` 示例。你如果想要，在 v1 冻结前（M14）加回来。
- 所有热路径钩子都提供 C ABI：首发工作量与风险过大。推迟到按需逐个加入（每个新钩子 = 新的 `_v1` 符号，不影响已有）。
- 不提供 C ABI：偏离最大。否决。

## 后果

第三方现在可以用 C 扩展授权；其他钩子在 v2 之前需要用 Rust 写并重新编译。示例：`examples/dylib-deny-uid`（含一个 `abi_version = 2` 的坏插件）。
