# ADR-0031 M2 补齐的 RDMA 插件细节

- 状态：accepted（主管于 2026-10-21 按 design.md 开头的例外条款决定：都是规格漏写或需要收紧的技术细节，不改变 semantics.md 的承诺，第 ① 条让"客户端碰不到服务端内存"的承诺更牢靠）
- 日期：2026-10-21
- 性质：插件细节（design.md 第 4 章 4.1）与两处第 3 章注记（3.3.2、3.6.4）；线上格式只新增插件私有的 0x0600 帧与描述符表布局
- 是否触及契约层：部分（描述符表布局、0x0600 RdmaSetup 帧都有金样）
- 相关章节：design.md 3.3.2、3.6.1、3.6.4、4.1；ADR-0009、ADR-0018、ADR-0022；ADR-0015（RDMA 本机不做实机测试）

## 背景

M2 写 rdma 插件时发现规格有几处没写死，还有一处写法有安全漏洞。插件代码本机无法实测（4 个 mlx5 端口链路全部 DOWN，人类决定不做实机测试），所以这些决定都配了不需要设备的单元测试（假网卡、假 sysfs），并经过一轮对照 sideway 0.4.3 源码的逐行审查。

## 决定

1. **QP 访问位两侧不同**（收紧 4.1 原文"INIT 的访问位要 LocalWrite | RemoteWrite | RemoteRead"）：accept 侧（接收请求的一方，服务端）的 QP **永不**开放远程读写；connect 侧（发请求的一方）在握手完成（`mark_authenticated`）之后，用 RTS→RTS 的 `modify_qp` 打开 RemoteRead/RemoteWrite。理由：RDMA 操作永远由"接收请求的一方"发起，accept 侧根本不需要被远程访问；原写法下，未认证的对端只要猜中 rkey，就能读写服务端整个内存池。
2. **握手里的协议 feature 位 `BULK_REMOTE` 首发不协商**：描述符表只出现在 rdma 插件两端之间，由插件自己设置与解析（帧头 flags 的 bit1/bit2），两端必然都是 rdma 插件。tcp 插件收到带这两个标志的帧会断开。core 的 `OUR_FEATURES` 保持 0。
3. **描述符表布局**：小端。`BULK_REMOTE` 的表在前，格式为 `n: u8` 后跟 n 个 16 字节 `{addr: u64, rkey: u32, len: u32}`，n 为 1..=16，每段 len > 0，Σlen = bulk_len。`REPLY_REMOTE` 恰好 1 个描述符，不带 n。长度为 0 的 bulk 段不写进描述符表。接收方先校验（n、len、Σlen、addr + len 不溢出）再发起 READ。
4. **RdmaSetup（0x0600）**：标准 48 字节帧头加 postcard body `{qpn, psn, gid, mtu}`，psn 取随机数的低 24 位。金样在 `plugins/rdma/setup.golden`。
5. **接收槽**：每条连接实际占 17 个 S 档槽位，即 16 个接收槽加 1 个发送暂存槽。3.6.1 的启动校验算式仍按 16 个算（`max_qps × 16 × 128 KiB ≤ S 档的 50%`），满载时实际约占 53%。校验只在 listen 一侧做；connect 一侧当场取不到槽位就返回 `BUSY`。
6. **信用控制**：同一连接在途请求达到 16 个时，`send` **一直**阻塞写线程，直到有回复还回信用或连接关闭（`ECONNRESET`），不设期限。这与 3.6.4 表格原文一致，两种传输对 core 的语义也就相同。等 SEND 完成仍最多等 `write_timeout_ms`。
7. **已知差别，首发接受**：同一连接上 16 个请求都超过 15 s 没回复时，客户端的保活 Ping 拿不到信用，两端 15 s 收不到帧，按"对端已死"断开并重连。这些调用早在 10 s 的 RPC 超时时就已结束；tcp 下这种情况不断连接。要彻底消除，得给保活单独留接收槽，会改 3.6.1 的槽位数与启动校验算式，不值得。
8. **设备与 GID 可以省略**：按引导连接本端的 IPv4，在 sysfs 里选端口 ACTIVE 的 RoCE v2 IPv4 映射 GID；node.toml 里写了 `device`/`gid_index` 就只在符合的项里找。本机没有能用的设备时 `connect` 返回 `EINVAL`，RpcClient 不会白白重试。
9. **推迟打开设备**：`[plugin.rdma] listen` 默认为空，此时 `listen()` 返回 None；`register_region` 只记下区域；第一次真正需要设备时才打开它并 `reg_mr`。所以默认编进 rdma 的二进制在没有 RDMA 的机器上也能正常运行。
10. **构建**：rdma 默认编进二进制，sideway 经 rdma-mummy-sys 在运行时 dlopen libibverbs，构建时需要 cmake 与 libclang。sideway 的依赖 `proc-macro-error2` 会触发 cargo 的"将来不兼容"报告，`.cargo/config.toml` 关掉了这份报告的打印，不影响任何编译器警告。
11. **交给 M3 的 core 修复**：`RpcClient` 在多个线程同时对同一对端发第一次调用时会各自建连，只保留一条。对 rdma 来说，每次建连都在两端各占一个 `max_qps` 名额和 17 个槽位。M3（M2 之后 core 可以改）改成按 `(scheme, 地址)` 只让一个线程建连，其余线程等它的结果。

## 备选方案

- 照 4.1 原文给两侧 QP 同样的访问位：有上面第 1 条说的安全漏洞。否决。
- 给保活单独留接收槽与信用：要改第 3 章的槽位数与启动校验算式，只为一个极端情况。否决。

## 后果

rdma 插件的行为与 tcp 基本一致，差别只剩第 7 条。插件代码仍是"未在本机验证"，semantics.md 与 `plugins/rdma/docs.md` 如实写明。
