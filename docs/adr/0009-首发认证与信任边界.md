# ADR-0009 首发认证与信任边界

- 状态：accepted（人类于 2026-10-20 批准）
- 日期：2026-10-20
- 偏离条款：理念文档第 7 章 [默认]"信任模型：服务端强制授权，客户端不可信"的具体落地；第 11 章 [待定]"客户端是否可信（假设：不可信）"
- 是否触及契约层：**是**（授权位置、认证方式、能力令牌）
- 批准类别：**需批准**（安全边界，A 栏：要你拍板）；确认批次 0（M0 开工前；M1 就实现握手）
- 相关章节：design.md 3.3.2、3.3.3、3.3.5、3.6.4、4.2、4.3、7.1、8.7；semantics.md 第 8 节

## 背景

首发的 authn 插件只有 `shared-key`；已验证依赖清单里没有 TLS、Kerberos 实现。理念文档要求服务端强制授权、客户端不可信。

## 决定

1. **服务端强制授权**：每个元数据请求都在元数据 leader 上经过 authz 管线（posix-mode → posix-acl → path-caps）；数据请求凭元数据签发的 HMAC 能力令牌（带 ino、epoch、权限、会话、layout 的链列表、变换参数、过期时间），数据节点只验签、不查元数据。
2. **主机级认证**：客户端机器用一把 key 做 HMAC 挑战-应答（密钥不在网络上传输），双向认证。key 的元数据（角色、租户、uid 范围、root_squash、path-caps、撤销标记）存在**复制状态**里（KEYMETA），所有节点一致。
3. **角色只有一套编码**（`Role { Admin = 1, Client = 2, Server = 3 }`，线上与 KV 里存 u8），握手时由 core 强制：key 0 只能是 Server；其他 key 声明的角色必须等于 KEYMETA 里的角色，否则 `AUTH_FAILED`。每个消息族有固定的角色权限表（例如只有 Server 能发 PeerCall、RaftMsg）——client key 冒充不了服务端。
4. **uid 由已认证的主机声明**，只在该 key 允许的 uid 范围内被相信；`root_squash` 把 uid 0 映射为 65534（除非 key 显式允许 root）。这与 NFS AUTH_SYS + 主机密钥同级。
5. **首发不加密线上流量**（无 TLS）：只在可信网络中使用（写进 semantics.md 与 ops.md）。管理 API 的写请求带签名与时间戳，5 分钟窗口内可被重放（ADR-0005）。
6. 服务端之间彼此信任（共享 `cluster.key`）；RDMA 下 rkey 只随每个请求的描述符给出（请求方给出自己缓冲的 rkey），服务端从不向客户端发请求，所以客户端永远拿不到服务端的 rkey。`cluster.key` 由管理员手工复制到新机器，从不经网络传输。

## 备选方案

- **Kerberos/GSSAPI**：逐用户强认证，但需要 KDC 等外部设施，违背"零外部依赖"。作为将来的 authn 插件。
- **双向 TLS**：需要引入 TLS 库；可作为将来的传输插件（不改本体）。
- **完全信任客户端**（HPC 传统）：理念文档说只在单团队内部可接受。否决为默认。

## 后果

- 被攻破的客户端主机可以冒充其 key 允许范围内的任何 uid；网络窃听能看到数据——必须写进对外文档。
- 每把 key 的权限可以收紧（uid 范围、path-caps、只读根），并可随时撤销（已建立的连接在集群图更新时关闭）。
