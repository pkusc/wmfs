# ADR-0028 命名空间语义与 cto 缓存失效协议 v1

- 状态：accepted（人类于 2026-10-20 批准）
- 日期：2026-10-20
- 性质：契约层首次定义（理念文档第 3 章第 1 行"命名空间语义与一致性模型"：POSIX 子集、rename 原子性、可见性规则、缓存失效协议、`consistency` 的 `cto` 等级；同一行的 `strong` 等级见 ADR-0013，新增放松项见 ADR-0014）
- 是否触及契约层：**是**
- 批准类别：**需批准**；确认批次 0（B 栏：技术契约。M4 实现命名空间、M6 实现缓存失效）
- 相关章节：design.md 3.1.1–3.1.4、3.5.3、3.5.6、8.1–8.4、8.6；semantics.md 第 2–3 节

## 背景

理念文档第 3 章把"命名空间语义与一致性模型"列为 [固定] 契约："所有插件依赖同一套'何时可见'的定义；两个插件理解不同就会静默丢数据"。0018–0027 都没有覆盖它的首次定义；没有获批的 ADR，M4（命名空间）与 M6（FUSE 缓存）就会在没有契约的情况下实现这些规则。锁语义与"删除后仍打开"的孤儿规则也需要写死。

## 决定

1. **POSIX 子集**（design.md 3.1.1 的"支持"与"不支持"两行）：普通文件、目录、符号链接、硬链接（仅文件）、mknod、rename（含 NOREPLACE/EXCHANGE）、chmod/chown/utimensat/truncate、fallocate mode 0、xattr 与 POSIX ACL（有默认 ACL 时新建对象不应用 umask——客户端协商 `FUSE_DONT_MASK`，由服务端决定）、fcntl 锁与 flock、O_APPEND/O_EXCL/O_TRUNC/O_DIRECT/O_SYNC/O_DSYNC、fsync、稀疏文件、删除后仍打开、statfs、readdir/readdirplus；不支持的一律返回明确错误。
2. **rename 原子性**（3.1.2）：整个命名空间在一个 raft 组里；rename 是执行器里的一个闭包、写集进一个 raft 条目，对所有观察者要么旧名存在、要么新名存在；目录不能移进自己的子树；跨配额域按被移动对象的用量检查目标配额；移动目录让 `attr_epoch` 加一并触发协调。
3. **可见性规则**（3.1.3 的六条）：元数据在 leader 上线性一致；数据在链上所有成员提交后才回复写者，且只有 `CommitWrite`（校验 layout epoch）成功后才属于文件；cto：写者 `close()` 返回后，之后任何节点发起的 `open()` 一定看到；文件打开期间每次读到的 chunk 都是某个已提交版本；锁即同步点；持久性按 3.1.3 第 6 条（cto 的 `O_DIRECT` 写与 strong 写一样同步提交）。
4. **缓存失效协议 C1–C6**（3.1.4）：没有服务端回调；C1 内核 TTL = `min(目录属性 attr_ttl, 挂载上限)`（strong = 0）；C2 open 时线性一致地取属性，change_id 变了先 `inval_inode` 再回复；C3 加锁后失效；C4 `STALE_LAYOUT` → 重新取 layout 重写，且任何改了 size 的 SetAttr 都回新的 layout 与 cap（所以 `O_TRUNC`——内核先 OPEN 再 SETATTR(size=0)——之后的写直接进新 epoch）；C5 读到 `CHUNK_NOT_FOUND` 先确认 epoch 未变；C6 集群图按 map_epoch 刷新。
5. **截断与 inline**：截断到 0 换新 epoch 并按当前属性重建 layout；`len(INLINE) ≤ size` 是不变式，所有改 size 的操作在同一批里维护它；cto 下 `O_DIRECT` 写走同步路径，数据留在调用方手里直到 `CommitWrite` 成功。
6. **锁语义**（3.5.3）：锁是复制状态，leader 切换不丢；所有者 = (session, lock_owner)；闭区间，"到文件尾"= `i64::MAX`（与内核 `OFFSET_MAX` 一致），所有入口归一、区间运算不溢出；`SetLock` 永远非阻塞，F_SETLKW 由客户端 lock-wait 线程持有回复对象、按退避轮询（不占 FUSE 线程，不保证先来先得；发起者正被致命信号杀死时立即回 `EINTR`，否则它会卡在内核里等回复）；释放时机：显式解锁、flush(lock_owner)、release 带 FLOCK_UNLOCK、会话关闭、驱逐第二阶段。
7. **孤儿 inode**（3.5.6）：最后一个链接删除 → 标记孤儿、立即从配额扣除；客户端心跳上报打开集合；gc 只在"不在任何存活会话的打开集合里、距 unlink 超过 2 个心跳周期、leader 就绪后所有会话都发过一次全集"时才删除。

## 备选方案

- 服务端回调 / 读委托（NFSv4 delegation）：能做更强的缓存，但要服务端到客户端的回调通道。二期。
- 只靠 TTL、open 时不校验 change_id：违反 cto（理念文档 8.2"下一次 open 后可见"）。否决。
- 服务端 FIFO 锁等待队列：执行器要挂起已执行过的闭包、重新生成授予操作，还要处理去重与超时，约多 150 行且容易写错；F_SETLKW 在 FUSE 线程上阻塞还会让 16 个等待者卡死整个挂载点。否决。
- 锁的"到文件尾"用 `u64::MAX`：内核 getlk 回复会得到 EIO，`end + 1` 会溢出。否决。
- 开 `FUSE_ATOMIC_O_TRUNC` 让 Open 带截断：Open 就变成写请求；而 ftruncate 改 size 本来就需要回新 layout。否决（保留"Open 只读 + SetAttr 回 OpenOut"）。

## 后果

所有插件与客户端按同一套"何时可见"的规则实现；内核行为相关的三点（umask、O_TRUNC 顺序、OFFSET_MAX）在 M6、M12 用小 spike 实测确认，有出入时改设计并更新本 ADR。
