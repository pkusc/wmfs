# ADR-0001 同步并发模型（不使用 tokio / async）

- 状态：accepted（人类于 2026-10-20 批准）
- 日期：2026-10-20
- 偏离条款：理念文档第 7 章 [默认]"语言：Rust（`tokio`、…）"；第 11 章 [待定]"最大规模：64 节点、数千客户端"的解读
- 是否触及契约层：否
- 批准类别：已同意（人类在需求中明确要求"不用 async"）；确认批次 0（知悉）
- 相关章节：design.md 0.1 D1、0.2、1.2

## 背景

理念文档默认使用 tokio。使用者是自述"基础不太好"的新手，需求里已承诺"不用 async"。目标规模是 1–64 节点的小集群。async 带来"函数染色"、难读的调用栈与难排查的挂起问题；raft-rs 的核心本身就是同步的。

## 决定

1. 全部代码只用 `std::thread` + `crossbeam-channel` + 阻塞 IO；不用 async/await、tokio、io_uring。
2. 线程按职责固定分池（design.md 1.2）：一个可变状态只有一个主人线程；线程之间只用通道或小粒度 `Mutex` 通信；**任何线程都不得一边持锁一边等网络**。
3. **线程池里的线程不等待网络响应**：链式复制的转发、同步传播用 `RpcClient::call_cb` 登记回调；回调在连接读线程（或超时时在 rpc-timer 线程）上执行，只把结果 `try_send` 进 repl 队列。阻塞式调用只允许出现在 FUSE 工作线程、CLI、后台任务、hb、sync 线程（它们不被别的节点依赖，每次最多等一个 RPC 超时）。**F_SETLKW 不在 FUSE 工作线程上等**：由客户端的 lock-wait 线程持有回复对象并轮询（design.md 8.6）。
4. **socket 只由每连接的写线程写**：每个连接一个读线程 + 一个写线程（栈 256 KiB）+ 一个有界发送队列（1024 帧）；其他线程发帧只是 `try_send`，队列满就断开这条连接；TCP 设 5 s 写超时，超时即断开。于是一个不读 socket 的坏客户端卡不住执行器、io、repl 线程。每个客户端到每个服务端只开 1 条连接，请求按 req_id 复用。
5. 首发规模目标：≤ 64 节点、≤ 1000 个客户端挂载（RDMA 下每个连接固定占 2 MiB 接收槽，客户端多时要调大内存池）。

## 备选方案

- **tokio async**：吞吐上限更高，但对新手复杂、调试困难，且与 raft-rs 的同步 API 需要额外桥接。否决。
- **只在网络层用 async、其余同步**：仍然要理解两套模型。否决。
- **回调里直接写 socket / 执行器直接回复**（不设写线程）：少一个线程，但一个慢客户端就能卡住全集群元数据。否决。

## 后果

- 好处：代码是普通顺序代码，调用栈可读；与 raft-rs、fuser、redb、tiny_http、ureq 的同步 API 天然契合。
- 代价：线程数随连接数增长（每连接 2 个）；限制了客户端数量（数千级）。更多客户端时可以写一个基于 epoll 的传输插件解决（传输插件化正是为此），协议不变。
- 必须显式设计"非阻塞转发"与"复制专用缓冲 lane"（ADR-0022、0024），否则阻塞模型下会出现分布式死锁。
