# ADR-0037 M6 补齐的挂载细节

- 状态：accepted（主管于 2026-10-23 按 design.md 开头的例外条款决定：都是规格漏写的技术细节，或已批准承诺的落实与措辞澄清，不增删功能）
- 日期：2026-10-23
- 性质：契约层补齐（`SetAtime` 的规则与上限、`AuthzOp::Handle` 的 C ABI 编号）、ADR-0036 的落实细节、几处实现取值
- 是否触及契约层：**是**（`constants.golden`、`meta.golden`、`docs/plugin-abi.md` 已更新，只增）
- 相关章节：design.md 3.3.4、3.7、8.1–8.5、9.5–9.7；semantics.md 2.2、3.2 第 4 条、"挂载"一节；ADR-0029、ADR-0033、ADR-0034、ADR-0035、ADR-0036

## 背景

M6 实现 FUSE 挂载、写回缓冲、O_DIRECT 同步写、内存块缓存与容器测试时，实现者与审查修复遇到下面这些规格没写死的地方，按最小方案做了、加了金样或测试，并上报确认。每一条在 design.md 对应位置都有"实现注记（M6）"。

## 决定

1. **`CommitWrite.close`**：客户端在写句柄 close（FUSE flush）时的那次提交带 `close = true`；只读句柄的 close 不写出、也不报告写者的错误；close 时没有要提交的数据就不发。服务端不用这个字段，不写进 changelog（在 ADR-0029 的 `SetSize` 里加一个对外的 `extra` 键是新的对外取值，而且 close 时没有数据就不提交，这个记号本来就不可靠）。以后（例如 M11 的协调器想更快知道写者关了）要用时，只用来更新 leader 内存里的打开集合。
2. **`SetAtime`**（relatime 的批量更新）：每一项要对文件有读权限（不满足的跳过）；atime 只往前走、不超过 leader 的当前时间；不改 ctime 与 change_id（否则每次读都会让别的客户端的缓存失效）；已删除的跳过；不写 changelog；一批最多 `SET_ATIME_MAX_ITEMS = 1024` 项（更多 → `EINVAL`，钉在 `constants.golden`）。`atime_due` 按 relatime：只在读方式打开普通文件、且 atime ≤ mtime、atime ≤ ctime 或已过 24 小时时设。
3. **`AuthzOp::Handle` 的 C ABI 编号是 21**（排在 `Admin = 20` 之后），从此固定。`docs/plugin-abi.md` 先只放编号表，其余在 M14 写全。
4. **ADR-0036 的落实细节**：
   - `O_TRUNC` 走不了 `TruncateHandle`：内核（6.17 的 `fuse_do_setattr`）为 `O_TRUNC` 发的 `SETATTR(size = 0)` 不带句柄，看起来与按路径截断一样，所以发 `SetAttr`。前一步的 Open 刚检查过写权限，结果相同；差别只在两个请求之间恰好有人 chmod。带写句柄的 ftruncate 照 ADR-0036 发 `TruncateHandle`。
   - 按路径截断先 `Open(O_WRONLY)`，照常检查写权限，然后才截 chunk。不会再出现"先用手上残留的写 cap 截了 chunk、SetAttr 才报 `EACCES`"的情况。
   - **布局变了之后重新取 layout**（3.1.4 C4：别人截断到 0、M11 的迁移）现在只能用 `Open`，要按当前权限检查。所以属主写一个已去掉写权限位的文件时，碰上布局变化会得到 `ESTALE`，与 ADR-0036 "属主自己的句柄照常可用"不一致。补法（M7 第一步）：新请求 `MetaOp::ReopenHandle { ino, write }`，追加在 `MetaOp` 末尾。它是 `Open` 的"经已打开的句柄"版本：授权用 `Handle`，走只读路径，签 cap 前核对会话，回 `Opened(OpenOut)`，inline 内容只给能读的人。客户端在 C4 为写句柄重新取 layout 时用它。约 20 行。
5. **锁**：M12 之前不协商 `FUSE_POSIX_LOCKS`/`FUSE_FLOCK_LOCKS`，fcntl 锁与 flock 由本机内核处理、只在本节点有效。这比让 getlk/setlk 回 `ENOSYS` 合理。semantics.md "挂载"一节写明"M12 之前"，属于分阶段的说明，M12 做完集群锁后删掉。
6. **cto 下跨节点的 `O_APPEND`**：内核按自己缓存的 `i_size` 算追加的偏移，open 时的失效通知不会刷新它。所以即使不是同时追加，另一个节点在属性缓存时长内刚追加过时，本节点的追加也可能从旧长度处写、覆盖它。这正是 semantics.md 3.2 第 4 条（原理念文档 8.2）说的"cto 下由各节点内核按自己缓存的长度计算偏移"，不是新的放松；措辞已补清楚。"挂载"一节的 cto 说明也注明"`O_APPEND` 的偏移除外"。
7. **两张 cap**：design 8.2 写每个 inode 一张 cap。客户端改为读、写各留最新的一张（`rcap`/`wcap`），换 epoch 时两张都丢掉。否则先写打开、再只读打开，写回就没有写 cap 可用。
8. **错误码**：RpcClient 的本地传输错误（`ECONNRESET`、`ETIMEDOUT`）在 `--op-timeout` 用完之后交给应用时一律变成 `EIO`；`lseek`、`poll`、`bmap` 用 fuser 默认的 `ENOSYS`（内核走通用实现）；`ioctl` 回 `ENOTTY`；`copy_file_range` 回 `EOPNOTSUPP`。
9. **写回**：每写满一个 chunk，由后台写线程提交一次，`new_size` 取这个 chunk 的末尾。服务端取最大值，所以提交到达的先后无所谓。客户端的属性只往前走（回复的 change_id 比手上的旧就不换）。写出失败时保留数据、记下错误，在之后的 write、fsync 或 close 报告；最后一个写者已经 close 之后再试一次仍失败，才丢掉数据并写日志（close 时已经报告过错误）。缓冲写的 `O_SYNC`/`O_DSYNC` 每次 write 都写出（WriteChunk → SyncChunks → CommitWrite）再返回。
10. **测试与工具**：
    - roadmap 演示改成 `diff -r --no-dereference`：`/usr/include` 里有指向树外的相对符号链接，任何拷贝（包括本地盘上的）都会悬空。"135 个文件大于 64 KiB"在本机属实。
    - pjdfstest 子集 = 12 个目录里所有不切换用户的测试文件（131 个文件、1034 个用例），全部通过，`tests/pjdfstest-expected.txt` 为空。
    - 容器里以 root 直接挂载时，mountinfo 的类型是 `fuse`（不是 `fuse.wmfs`），按来源 `wmfs:<集群>` 识别（M7 的路径映射同样这样做）。
    - 本机有个进程（moshi-hook）会去连新打开的 127.0.0.1 端口，所以测试一律不按"服务端接受了几条连接"断言，改数客户端自己建连的次数（M5 那个偶发失败的根因）。
    - `wmfs dev up --profile minimal` 在 init 时选定（default 类 1 副本、不写 `/home`、`/scratch` 的 replicas、node.toml 禁用 quota 与 mclock）；已有的开发集群是别的 profile → 报错并提示 `wmfs dev down --purge`。nas-safe、hpc-rdma 从 M9 起。
11. **按 roadmap 留给后面的**：`wmfs dev mount --node`（M13 的 locality）；集群锁与 strong 下的 `AppendReserve`（M12，也要用 `Handle` 授权）；会话驱逐后的句柄处理与 `want_quota`（M10）；`--cache local-nvme`（M13）。

## 留给 M7 第一步的小修

12. 第 4 条的 `ReopenHandle`。
13. readdir 快照里 `..` 的 inode 号现在是目录自己的：改成它的父目录（客户端在 lookup、mkdir、readdirplus 与自己的 rename 时记下目录的父 inode；根目录的 `..` 是它自己）。
14. `wmfs dev mount` 失败时保留 `mount.log`（只删 pid 与挂载点记录），错误信息里指向的日志文件要还在。

## 后果

挂载这一层的取值从 M6 起固定，由金样与测试守住；后面的里程碑只增不改。第 12–14 条在 M7 第一步修。
