# ADR-0030 M1 补齐的握手、帧级约定与管理 API 细节

- 状态：accepted（主管于 2026-10-21 按 design.md 开头的例外条款决定：都是规格漏写的技术细节，不改变 semantics.md 的任何承诺、不增删功能）
- 日期：2026-10-21
- 性质：契约层补齐（线上协议 v1、管理 API、数据目录里的 NODE 文件）
- 是否触及契约层：**是**（都已有金样固定）
- 相关章节：design.md 3.2.1、3.3.2、3.3.3、3.3.8、3.6.4、3.12、7.1；ADR-0005、ADR-0009、ADR-0018、ADR-0020

## 背景

M1 实现传输与认证时，发现规格没有写死下面这些会上网络或落盘的细节。实现者按最小方案做了、加了金样，并上报确认。

## 决定

1. **握手证明的整数编码**（3.3.2）：`proof` 与 `server_proof` 的 HMAC 输入里，`role` 占 1 字节，`key_id` 是 4 字节大端（与派生 `secret(k)` 时的 `k_be32` 一致），`cluster_id` 用 Hello 里的 16 字节（客户端还不知道时全 0）。金样：`tests/golden/auth.golden`（已用独立的 Python HMAC 交叉核对）。
2. **握手被拒时的回复**：服务端回一帧 `kind = Response`、`msg_type` 沿用被拒的请求（Hello 或 Auth）、带 `ERROR` 标志，然后关闭连接；第一帧不是握手帧时直接关闭，不回复。
3. **保活**：只有客户端发。客户端连接的写线程空闲满 5 s 发一个 `req_id = 0` 的 Ping，回复忽略；**握手完成之前不发**。服务端从不向客户端发请求；任何一端 15 s 收不到帧就认为连接已死（读超时）。
4. **回复超过上限**（3.3.8）：服务端要发的回复超过协议或该传输的帧上限时，改发同 `req_id`、同 `msg_type` 的 `ERROR(FEATURE_UNSUPPORTED)`，只让这一个请求失败，不断开连接（落实 ADR-0018 第 7 条"只有帧超过该传输的上限只让单个请求失败"）。
5. **回复缺 bulk**：客户端收到 `bulk_dropped` 的回复（接收方内存池满，丢掉了 bulk）时按 `BUSY` 处理并重试（3.6.4 原来只规定了请求与 OneWay 的情况）。
6. **NODE 文件**（3.2.1）：数据目录里的 `NODE` 是 TOML，字段依次为 `format`、`cluster_id`、`node_id`、`created_ms`，原样文本有金样。
7. **管理 API**（7.1）：
   - 新增 `GET /api/v1/failpoints`（任何已认证的 key；`wmfs failpoint list` 要用）。GET/POST/DELETE 都回 `FailpointList`；`failpoints_api = false` 时整组返回 404。清除一个没设置过的 fail point 回 404；fail point 名字只允许 `[A-Za-z0-9._-]`。
   - 错误 JSON 里的 `error` 是小写的错误码名（`auth_failed`、`eacces`、`einval`、`enoent` 等）。
   - `GET /api/v1/health` 的结构：`{ok, version, cluster_id, node: {node_id, addrs, mgmt_addr}, meta_role, leader, audit_lag}`。
   - 签名算法的测试向量在服务端（`core/tests/golden_net.rs`）与 `wmfs-mgr`（`SIG_GOLDEN`）两边各固定一份。
   - 声明 body 超过 1 MiB 的请求：不回复，连接挂起。原因：tiny_http 0.12 丢弃没读完的 body 时，会按声明的长度一次性分配内存，一个巨大的 `Content-Length` 就能让 server 进程因内存分配失败而退出。M1 的规避办法是不丢弃这种请求（`mem::forget`），代价是每个这样的请求占住一个 fd 和 tiny_http 的一个线程。tiny_http 也没有读超时：声明了 body 却不发送的连接会一直占住一个 `mgmt-http` 线程。
8. **上面第 7 条的风险首发接受**：首发的信任边界本来就是"只在可信网络上使用"（ADR-0009，没有 TLS）。管理端口能被同一网络里的恶意程序拖慢或耗尽线程，但不会让进程崩溃，也不会绕过签名。semantics.md 与 `docs/ops.md`（有了之后）要写明：管理端口只对可信网络开放。二期再考虑给管理端口自己写一个带读超时的小 HTTP 服务端，或换掉 tiny_http。
9. **3.12 接口只增不改**：M1 新增了 `RpcClient::new_with_role`、`client::default_role`、`check_reply`、`Responder::into_stream`/`StreamTx`、`RpcServer`/`Service`/`ServerId`、`InFrame::error`，已有签名没有变。以后里程碑给骨架接口**只增不改**时，在 design.md 对应位置写实现注记即可，不需要新 ADR；要**改**已有签名，仍按契约变更处理。

## 备选方案

- 现在就自己写管理端口的 HTTP 服务端（约 200 行）：可以根治第 7 条的风险，但代码量预算只剩几百行，而且在可信网络的前提下这不是首发必须的。推迟到二期。
- 把这些细节留到以后再定：它们已经在网络和磁盘上出现、已有金样，留着不定只会让后面的里程碑各猜各的。否决。

## 后果

线上协议 v1 与管理 API 的这些细节从 M1 起固定，由金样守住。管理端口在不可信网络上的拒绝服务风险是已知限制，如实写进文档。
