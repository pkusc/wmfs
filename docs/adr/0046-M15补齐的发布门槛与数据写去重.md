# ADR-0046 M15 补齐的发布门槛与数据写去重

- 状态：accepted（主管于 2026-11-21 按 design.md 开头的例外条款决定）
  - 第 1 条是修补 M15 审查发现的数据写重试线性一致性缺陷，兑现 `semantics.md` 2.3 已承诺的"单个 chunk 内的读写线性一致"；不增删对外功能，不放松语义承诺。
  - 第 2 条确认一个首发不做的协议改动并如实写明；第 3–5 条确认 M15 补齐的测试设施、发布门槛口径与最终行数。
- 日期：2026-11-21
- 性质：
  - 修补数据面重试去重缺失（并发写者下丢回复/换链头时的线性一致性）；
  - 确认已有节点事后修改传输地址的首发边界；
  - 确认 M15 发布门槛、profile 全套与最终行数收口。
- 是否触及契约层：**是**。
  - `DataOp::WriteChunk`、`DataOp::TruncateChunk` 末尾各加 `write_id: u64`，`ForwardWrite` 末尾加 `dedup: (u64, u64)`（第 1 条，金样 `data.golden` 与 `peer.golden` 随之更新）。首发前各节点与客户端同版本，与 ADR-0043 第 3 条、ADR-0044 第 5 条同理。
- 相关章节：design.md 2.2、3.3.5、3.3.6、3.3.8、3.4.2.3、3.4.3、3.4.5、3.11、9.5–9.7；semantics.md 2.3、10；ops.md 1.2、6；ADR-0015、ADR-0041、ADR-0043、ADR-0044、ADR-0045。

## 背景

M15 完成了首发的发布门槛与最终收尾：
- 三个 profile（`minimal`、`nas-safe`、`hpc-rdma`）定稿与 `scripts/profiles.sh --full`；
- 容器内完整 `pjdfstest`、每个 profile `fsx` 10 万次、`fsstress`、`IOR`/`mdtest` 冒烟；
- `net.drop.to/from.<节点>`、`net.delay` fail point 与 `tests/it/chaos.rs`（kill -9、SIGSTOP、分区、网络延迟、时钟偏移 + Jepsen-lite + 客户端零错误）；
- `scripts/accept.sh profile-minimal | profile-nas-safe | profile-hpc-rdma | chaos | release`；
- `docs/semantics.md` 与 `docs/ops.md` 定稿。

实现、审查与验收过程中上报了两个需要定夺的协议层问题（`design.md` 3.4.3 与 9.5 的 M15 注记），同时确认 M15 的发布门槛细节与最终代码规模。

## 决定

### 修补数据面并发写重试的线性一致性

1. **数据写与截断按 `(chunk, session, write_id)` 沿链去重**：
   - **问题**：M15 审查时发现，把单个 chunk 的 Jepsen-lite 寄存器加长到 1000 个操作、约八次捣乱时，偶发判为不线性一致；进程内用 `net.drop.from.<head>` 稳定复现：写者 A 的 `WriteChunk` 已在链尾提交并被读到，但 head 给 A 的回复丢了（网络丢包或 head 被 `kill -9`）；随后写者 B 写入新值并成功返回；A 的 `DataClient` 超时重试后，旧 head 或新 head 把重试当成新写分配更高版本号，覆盖了 B 之后完成的写，违反 `semantics.md` 2.3 "单个 chunk 内的读写线性一致"。
   - **线格式（首发前最后一次补齐）**：
     - `DataOp::WriteChunk` 与 `DataOp::TruncateChunk` 末尾各增加 `write_id: u64`。`DataClient::write` 与 `DataClient::truncate` 在进入重试循环前各生成一次非零随机 `write_id`（`rand::random_u64().max(1)`），同一次调用的所有重试沿用同一个 `write_id`；`write_id == 0` 表示不启用去重（供组件测试手工构造请求）。
     - `ForwardWrite` 末尾增加 `dedup: (u64, u64)`，值为 `(cap.session, write_id)`；增量转发（`first_send`）与完整重发（`NeedFull`、`redrive`）均携带它。
     - 更新 `tests/golden/data.golden`（`DataOp.WriteChunk`、`DataOp.TruncateChunk`）与 `tests/golden/peer.golden`（`PeerOp.ForwardWrite`）。
   - **去重表与登记时机**：
     - 每个数据节点在内存中维护 `WriteDedup`（`core/src/data/dedup.rs`），以 `(ChunkId, session, write_id) → version` 映射；按单调时钟保留 5 分钟（`DEDUP_TTL_MS = 300_000`，大于默认 `--op-timeout` 120 s 与允许的时钟偏差），每节点上限 65,536 条，查询与登记均为 O(1)。
     - head 在 `write::step` 确认本地视图仍是 head 后立即查 `node.dedup.get(chunk, (cap.session, write_id))`，命中则直接回复原版本号 `Written { version }`，不再写盘也不推进版本。
     - 所有本地提交路径均登记去重表：单节点写入、空 chunk 截断、`forward::settle`（**先于** `chunks.finish(id)` 登记，保证在途期间到达并排队等待的客户端重试在被唤醒后立即命中去重）、3.4.2.6 规则 2 的 `commit_local`，以及 `replica::apply` 命中 `committed >= fw.version` 的重复转发分支。
   - **测试覆盖**：`core` 单元测试 `data::dedup`、`tests/it/craq_edges.rs::retried_writes_and_truncates_deduplicate_across_head_failover`（覆盖写与截断经连续换主 `[1,2,3] → [2,3] → [3]` 的去重）以及 `tests/it/failpoint_net.rs::dropped_head_reply_retry_stays_linearizable`（精确复现 M15 审查场景）。
   - **已知残余（写进 `design.md` 3.4.5）**：去重表只存内存，不落盘，也不随重同步的 `FetchChunk` 传输。因此若整条链同时重启、或在某次回复丢失后原链上所有 Serving 成员都在客户端完成重试前被仅经 `FetchChunk` 同步进来的新成员全部替换，重试仍可能重新生效。此类场景概率极低且与首发简洁目标权衡后接受。

### 首发不做、如实写明的

2. **已有节点事后修改传输配置不更新 `NodeRecV1.addrs`**：
   - `--profile hpc-rdma` 由 CLI 层按 `default` 的初始 KV 加上 `InitOpts::data_transport` 实现，`wmfs join --rdma` 经 `JoinOpts::data_transport` 随 `JoinReq.addrs` 公布 RDMA 地址，保持 `core/src` 除注释外不出现传输名（`design.md` 2.1、`scripts/ci.sh rules`）。
   - 已加入集群的节点事后修改 `node.toml` 更换数据面传输时，不提供动态重写集群 `NodeRecV1.addrs` 的协议操作（留作二期）；该限制已在 `docs/ops.md` §1.2 与 `docs/design.md` 3.4.3 如实写明。

### M15 基础设施与发布门槛确认

3. **网络故障注入与 `MetaClient` 换节点收口**：
   - 补齐 `design.md` 3.11 首批 fail point：`net.drop.to.<节点>`、`net.drop.from.<节点>`、`net.delay`（帧间不累加），热路径先查 `failpoint::active()`（`wmfs-api`）。
   - target 心跳识别 `leader_hint` 对应的节点号以使 `net.drop` 生效；`MetaClient` 换节点改为仅当失败节点仍是当前选中节点时才轮转，并记录放弃节点使同组等待调用经 `PendingCall::wait_timeout` 提前重发（避免冻住 leader 时并发超时一起轮转回原节点）。
4. **发布门槛与 profile 口径**：
   - `scripts/accept.sh` 新增 `profile-minimal`、`profile-nas-safe`、`profile-hpc-rdma`、`chaos`、`release` 入口；`scripts/profiles.sh <name> --full` 为发布门槛全套（不带 `--full` 保留给 M6–M14 阶段验收）。
   - 容器外部测试（完整 `pjdfstest`、每个 profile `fsx` 10 万次、`fsstress`、`IOR`/`mdtest` 冒烟）在 `--full` 与 `release` 中属于必过门槛：缺少 `wmfs-tools` 镜像时判 FAIL（不是 SKIP）。
   - `hpc-rdma` 在无 RDMA 设备的机器上明确输出 `SKIP`（未在本机验证，不算通过也不算失败；发布说明不得声称支持，符合 `semantics.md` §10、`ops.md` §6 与人类 2026-10-20 决定）。
   - `scripts/loc.sh` 发布门槛按非测试代码合计 ≤ 38,000 行（`within_limit`，ADR-0041 第 2 条）判定；`m15_docs` 检查对外文档与各插件 `docs.md` 齐全、无待办字样、全部 ADR 为 `accepted`。
5. **行数收口**：
   - M15（实现、审查修复、验收修复与本 ADR 数据写去重）共净增约 238 行非测试代码：最终非测试代码合计 **37,485 行 ≤ 38,000 行**，按模块重估总量 **Σ max = 37,935 行 ≤ 38,000 行**，`scripts/loc.sh` 中零模块超出估算。整个项目（M0–M15）未动用 `roadmap.md` §4 的任何简化储备。

## 后果

- 并发写者下丢回复或 head 崩溃换主时，数据写与截断的重试不再覆盖更新的写，`semantics.md` 2.3 的单个 chunk 线性一致承诺得以兑现。
- `tests/golden/data.golden` 与 `tests/golden/peer.golden` 在首发前完成最后一次更新。
- 全部 46 篇 ADR 均为 `accepted`，对外文档（`semantics.md`、`ops.md`、`plugin-abi.md` 及各插件 `docs.md`）定稿，发布门槛可由 `scripts/accept.sh release` 一键复现。
