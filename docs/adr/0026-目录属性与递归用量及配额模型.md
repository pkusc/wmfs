# ADR-0026 目录属性存储与继承、递归用量计数、配额 quantum 额度模型

- 状态：accepted（人类于 2026-10-20 批准）
- 日期：2026-10-20
- 性质：契约层首次定义（理念文档第 3 章"目录属性存储与继承""递归用量计数"；第 5 章；8.2"配额……超限幅度有上界并可配置"）
- 是否触及契约层：**是**
- 批准类别：**需批准**；确认批次 3（M7 开工前；决定 4 的配额模型是 A 栏：要你拍板）
- 相关章节：design.md 3.1.4、3.8、3.9、第 5 章；semantics.md 第 4、5 节

## 背景

最初的想法：每分配新 chunk / 扩展文件做一次 quota_admission，超限 ≤ chunk 大小 × 并发写者数。另有"预留"模型（零超限，但需要按会话的预留表、可能提前 EDQUOT、驱逐时清理）与 quantum 额度模型（零额外状态）。理念文档原则 3 要求每个可定制的行为都是目录属性——包括缓存时长这类行为参数，不能只放在挂载参数或插件配置里。

## 决定

1. **属性**：每个目录一条 DIRATTR；注册表定义每个键的种类（Inherit 取最近祖先 / Stacked 所有祖先同时生效——只有配额）、子键、解析与校验、生效方式、消费插件；**没有已启用插件消费的键不能设置**（只统计进程内插件和 core；进程外的 audit-log 不参与，所以 `audit` 的消费者是 core——它负责计算 audited 标记）；未知键报错；`inherit=false` 阻断 Inherit 键但不阻断配额；来源可查；属性修改与目录 rename 让 `attr_epoch` 加一（缓存整体失效）；所有变更写 changelog。属性字符串的切分、解析、规范化**在服务端做**（`POST /api/v1/attr {path, spec}`）。
2. **缓存时长是属性**：`consistency=cto,attr_ttl=1s`（子键，可继承，0–10 s）；挂载参数 `--max-attr-ttl` 只能把它调小。
3. **成功但警告**：声明无法满足（副本、条带，ADR-0016）、"新数据 + 协调器"类键对已有文件的提醒（ADR-0021）、审计消费者长时间没前进——都在 set 的回复里给出，不静默。`audit` 第一次被设为非 off 时同批创建 `CURSOR(audit-log)`，让 changelog 的保留与 410 机制对审计消费者生效。`encrypt=tenant:<名字>` 用 DATAKEY_NAME 点查。缺省值（`attr_ttl=1s`、`quota` 的 `grace=7d`、`quantum=64M` 等）只在注册表里，不在插件配置里。
4. **配额 = quantum 额度**（A 栏，推荐）：open/create 时授予 `quota_end = size + min(quantum, 剩余量)`；客户端越过额度前先提交已写长度并申请下一段，额度为 0 时 `write()` 立即 `EDQUOT`；没有任何预留表；服务端护栏：任何 scope 超过 `hard + 16 × quantum`，或单次增长超过 quantum 且超过硬限 → 拒绝增长；文件数、AppendReserve、fallocate、截断扩展、跨 scope rename 精确检查；quantum 默认 64 MiB，可逐目录配置。
5. **递归用量**：每个目录一条 RSTAT（子树内普通文件逻辑字节、非目录文件数、目录数、按存储类分计数），在同一个元数据事务里沿主父目录链更新到根；任意目录常量时间读取；硬链接只计主父目录；协调器全量遍历时自检。
6. 对外精度：守协议的客户端最多超出 `quantum × 同时写入的文件数`（单写者精确）；任何客户端最多超出 `16 × quantum`。

## 备选方案

- **预留模型**：硬限永不超过（更强），代价是每个 (会话, 文件) 的预留记录、驱逐时清理、"别人的预留导致提前 EDQUOT"。**如果你更看重"永不超限"，可以选它**（约多 300 行与一张表，在 M7 实现前加进 KV 布局）。
- 每个 chunk 一次 admission：语义同 quantum = chunk 大小，元数据请求多 16 倍。
- `attr_ttl` 只做挂载参数：服务端给出的 semantics 行不知道每个挂载的实际值，也违反原则 3。否决。

## 后果

配额可能短暂超限，但上界可查询、可配置，与理念文档 8.2 逐字一致；leader 切换不破坏上界（额度不是持久状态）。
