# ADR-0022 预注册内存池与零拷贝所有权规则（含复制专用 lane）

- 状态：accepted（人类于 2026-10-20 批准）
- 日期：2026-10-20
- 性质：契约层首次定义（理念文档第 3 章"缓冲区与内存模型"；原则 5"RDMA-first 的数据路径"）
- 是否触及契约层：**是**
- 批准类别：**需批准**；确认批次 0（B 栏：技术契约）
- 相关章节：design.md 3.6

## 背景

RDMA 要求：网卡读写的内存必须事先注册，并且在操作完成前不能被复用。用不实现 Clone 的 `Buf` 表达所有权。每个节点既是某些链的链头又是别的链的后继，若复制流量与客户端流量争同一个池，池满时会跨节点互相等待（分布式死锁或 RETRY 风暴）。客户端一个 chunk 的脏数据在一个 Buf 里、只需要发其中几段时，如果只能整块发送，就只能拷贝。

## 决定

1. 启动时一次 `mmap` 一整块内存，切成三档：128 KiB、4 MiB + 128 KiB、16 MiB + 128 KiB；永不归还给操作系统；每个传输插件启动时注册一次整块区域（RDMA 得到一个 MR）。默认：服务端约 1 GiB（S 256 MiB）、客户端约 768 MiB、`wmfs dev` 服务端约 384 MiB（S 128 MiB）、CLI 一次性命令约 70 MiB 的小池。
2. `Buf` 不实现 Clone：按值传递 = 所有权转移，Drop = 归还池；`freeze()` 得到只读、引用计数的 `FrozenBuf`；**`BufSlice { buf: FrozenBuf, off, len }` 表达子区间**，`OutFrame.bulk` 是 `Vec<BufSlice>`，各段在线上依次拼接（TCP 依次写；RDMA 用 n ≤ 16 个描述符，接收方依次 READ 进**一个** Buf）。RDMA 发送方持有这些 `BufSlice` 直到对端响应到达。
3. **复制专用 lane**：每档 25% 的槽位（向上取整，**至少 1 个**）只给复制流量（接收转发、FetchChunk 响应、打包 pending）；复制可借用普通槽位，普通流量不能借用复制槽位。
4. 没有线程无限期等待缓冲：普通请求取不到缓冲 → `BUSY`；连接读线程取缓冲最多等 100 ms，否则把这条消息的 bulk 读出丢弃（请求回 `BUSY`，OneWay 的 RaftMsg 直接丢弃），发送方保留 pending、稍后重发。
5. **RDMA 接收槽**：每个 QP 固定占 16 个 S 档槽位；启动时校验 `max_qps × 16 × 128 KiB ≤ S 档的 50%`，不满足就拒绝启动并写明需要的大小。
6. **客户端写回缓冲按槽位计**：每挂载最多占 M/L 档槽位的 60%，每 inode 最多 16 个槽位，其余留给读路径；`chunk ≤ 128 KiB` 用 S 档。
7. pending 表不持有缓冲（重新驱动时从 pending 文件重新读取）。
8. 只有"接收请求的一方"发起 RDMA 单边操作；rkey 只随请求的描述符给出；客户端永远拿不到服务端的 rkey。
9. `unsafe` 只允许在 `buf/pool.rs`、`base/sys.rs`、`hooks/cabi.rs`、`plugins/rdma/`。

## 备选方案

- 每个请求一个 `Vec<u8>`：无法 RDMA 注册，违反原则 5。否决。
- 按需增长的 slab：注册回调更复杂。否决。
- 不分 lane：有分布式死锁风险。否决。
- RDMA 接收槽单独一块 8 KiB 小槽：body 大于 8 KiB 的数据族消息（16 MiB chunk 的 ForwardWrite、ListChunks 回复）就要另走 bulk，多一条路径。否决（改为"从 S 档取 + 启动校验"）。
- 只发整块 FrozenBuf：发几段 extent 时只能拷贝或各自发明切片类型。否决。

## 后果

内存在启动时固定占用；过载时以 `BUSY` 背压，客户端退避重试；RDMA 连接数受内存池大小约束（写进 ops 文档）。
