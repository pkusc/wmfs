# rebalance 后台任务

**钩子**：bg_task（只在元数据 leader 上跑，每轮结束隔 10 min）
**fail point**：`plugin.rebalance.bg_task`（本体包在每一步外层）　**指标**：`wmfs_rebalance_files_moved_total`（另有框架的 `wmfs_task_*`）

## 它做什么

数据放在"链"上（几台机器上的几个副本）。新文件按 label-match 的规则优先放进更空的链，但已有的数据可能不均匀（例如后加入的节点是空的）。
rebalance 盯着同一个存储类（同副本数）的链：最满的与最空的**使用率**（链上最满的成员的 已用 / 容量）相差超过 **20%** 时，把最满那条链上的
文件挪到别的链上，差距小于 **10%** 就停（design.md 4.12）。

挪法与协调器相同（迁移原语）：给文件分一个新的 epoch、按存储类选链时排除最满的那条、拷数据、切换布局；内容不变，读写不中断。

用量来自各节点每秒一次的心跳；旧布局要等文件没人打开、过了宽限期才删，所以用量降得比搬得慢。为了不搬过头，一轮最多搬"两条链已用之差的一半"
那么多字节。

## 配置

没有部署参数。限速：`wmfs task set rebalance bw=50M`；暂停：`wmfs task pause rebalance`。

## 诚实说明

- 首发的小集群里一个节点一个 target、三副本时，每条链的成员都一样，使用率天然相同，rebalance 什么也不做；它对"链比节点多、副本少于节点数"的
  部署才有用。
- 一直写打开的文件会被跳过（与协调器相同）。
- 不会降低文件的条带数：排除最满的链之后，剩下的链不够放下一个多条带文件的全部条带时，这个文件不搬。
