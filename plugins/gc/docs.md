# gc 回收插件

**钩子**：bg_task（在元数据 leader 上运行，每轮结束隔 1 s 再开始下一轮）　**热路径**：否
**fail point**：`plugin.gc.bg_task`（本体包在每一步外层，触发 = 这一步失败，1 s 后从同一个游标重试）
**指标**：`wmfs_gc_epochs_deleted_total`、`wmfs_gc_orphans_deleted_total`，以及框架的 `wmfs_task_*{task="gc"}`

## 它做什么

删除已经没人要的数据（design.md 4.12、3.5.6、3.4.2.9）：

- **废弃的 epoch**：文件被截断到 0（`O_TRUNC`、覆盖式 `cp`）时，元数据换一个新 epoch、旧 epoch 的 chunk 一下子全部不可达，同时写一条
  GC 记录。过了宽限期 `epoch_gc_grace`（集群运行参数，默认 60 s；还拿着旧 layout 的读写会按 C4/C5 刷新，所以设成 0 也安全）之后，
  gc 对这个旧 epoch 用到的每条链发 `DeleteEpoch`，数据节点删掉整个目录，然后删记录。
- **孤儿 inode**：最后一个名字被删掉、但可能还有人打开着的文件。只有三个条件都满足才删：没有任何客户端打开着它（元数据 leader 内存里
  的打开集合）；距删除已超过 6 s（刚 open 的客户端来得及上报）；本 leader 就绪已超过 6 s，且每个还活着的会话都在这之后报过一次
  完整的打开集合（换过 leader 时内存里的集合是空的，不能信）。然后删数据、最后删 inode。

每一步只处理 ≤ 100 条记录，而且可以重放（删过的再删一次什么也不做），崩溃或换 leader 之后从保存的游标接着做。

## 配置

没有部署参数：宽限期是集群运行参数（`wmfs cluster set epoch_gc_grace=0s`，M7），限速用 `wmfs task set gc …`（M11）。

## 诚实说明

M5 只做上面两种；被驱逐/已关闭会话的去重记录、过期的驱逐记录、changelog 修剪、数据节点上"离线期间错过删除"的本地孤儿扫描在 M11。
一个崩溃了的客户端的会话在会话租约驱逐（M10）之前一直算"存活"，这期间它没有重发打开集合，孤儿会一直等着（宁可晚删，不错删）。
