# gc 回收插件

**钩子**：bg_task，两个任务——`gc`（在元数据 leader 上运行，每轮结束隔 1 s 再开始下一轮）与 `gc-local`（在每个数据节点上运行，
每 10 min 一轮）　**热路径**：否
**fail point**：`plugin.gc.bg_task`（本体包在每一步外层，两个任务都是；触发 = 这一步失败，1 s 后从同一个游标重试）；
`gc.local.min_age_ms`（测试用：`return(<毫秒>)` 把本地孤儿扫描的"目录至少这么旧"改小）
**指标**：`wmfs_gc_epochs_deleted_total`、`wmfs_gc_orphans_deleted_total`、`wmfs_gc_dedup_deleted_total`、`wmfs_gc_changelog_trimmed_total`、
`wmfs_gc_local_epochs_deleted_total`、`wmfs_gc_local_chain_dirs_deleted_total`，以及框架的 `wmfs_task_*{task="gc"|"gc-local"}`

## 它做什么

删除已经没人要的数据与元数据（design.md 4.12、3.5.6、3.4.2.9）。

leader 上的 `gc` 一轮依次做四段：

- **废弃的 epoch**：文件被截断到 0（`O_TRUNC`、覆盖式 `cp`）、或被后台协调器换了布局时，旧 epoch 的 chunk 一下子全部不可达，同时写一条
  GC 记录。截断、覆盖写换下来的（kind 2）过了宽限期 `epoch_gc_grace`（集群运行参数，默认 60 s）就删——之后还拿着旧布局的读者按 C5 看到
  截断，一直开着日志文件的程序在 copytruncate 式轮转之后也不泄漏空间；协调器换下来的旧布局（kind 3，内容与新布局相同）还要等**没有人
  打开着这个文件**（拿着旧布局的读者照样读得到，关掉之后再删；同孤儿的三个条件，ADR-0042 第 5 条）。然后 gc 对这个旧 epoch 用到的
  每条链发 `DeleteEpoch`，数据节点删掉整个目录，最后删记录。
- **孤儿 inode**：最后一个名字被删掉、但可能还有人打开着的文件。只有三个条件都满足才删：没有任何客户端打开着它（元数据 leader 内存里
  的打开集合）；距删除已超过 6 s（刚 open 的客户端来得及上报）；本 leader 就绪已超过 6 s，且每个还活着的会话都在这之后报过一次
  完整的打开集合（换过 leader 时内存里的集合是空的，不能信）。然后删数据、最后删 inode。
- **去重记录**（M11）：每个写请求在元数据里留一条"它的结果"，网络重试时原样返回；会话关掉或被驱逐之后，它的这些记录就没用了，分批点删。
- **changelog 修剪**（M11）：所有消费者游标都读过的、超过 7 天的、比最新的旧 1000 万条以上的，从最旧的起删掉；之后再读更早的位置会得到
  `410 Gone`（缺口是显式的，不是静默的）。最后顺带删掉过期的驱逐记录（保留 24 h，M10）。

每个数据节点上的 `gc-local`（M11，本地孤儿扫描）：

- 列出本节点每个 target 上的 `(链, ino, epoch)` 目录（一轮每个 target 只列一次），按批问 leader 它们死了没有（文件不在了，或这个 epoch
  既不是它现在的、也不是正在迁移的，也没有 leader 的 gc 还管着的记录）；死了的、而且目录的修改时间早于 1 小时（与 `epoch_gc_grace` 取大）
  的整个删掉。清理的是：节点离线期间错过的删除、gc 删过之后才迟到的数据（例如旧 leader 没做完的小文件转存）。leader 的 `gc` 还管着的
  旧 epoch（有 GC 记录：还在宽限期里的、文件还打开着的迁移）不归它。
- 这个 target 已经不是成员、链也不在等它回来的链目录整个删掉（它回不去了；以后要用它会重新同步）。宁可不删：本节点与 leader 失联、集群图里
  没有这条链、这条链在本 target 上 1 小时之内还写过东西，都不删。

每一步只处理一小批（GC 记录 ≤ 100 条、去重记录与 changelog ≤ 1000 条、本地目录 ≤ 200 个），而且可以重放（删过的再删一次什么也不做），
崩溃或换 leader 之后从保存的游标接着做。M9 起有多副本的链：`DeleteEpoch` 沿链传播，每个副本都删；一条记录删不成（例如它的链此刻没有
正常服务的副本——等最后的副本回来）只跳过这一条、计入积压，下一轮再试，不挡住同一页里别的记录；没有正常服务副本的链不发请求，不必每条
都等满 30 s。

## 配置

没有部署参数：宽限期是集群运行参数（`wmfs cluster set epoch_gc_grace=0s`，M7）；`wmfs task run gc`（或 `gc-local`）马上来一轮，
`wmfs task set gc …` 限速，`wmfs dev wait task-idle gc` 等这一轮做完（M11）。

## 诚实说明

- 一个崩溃了的客户端的会话在会话租约驱逐（M10）之前一直算"存活"，这期间它没有重发打开集合，孤儿与旧 epoch 会一直等着（宁可晚删，不错删）。
- 客户端经会话心跳（约 3 s 一次）报告打开集合，所以 gc 至少等写记录之后 6 s 才删协调器换下来的旧布局，哪怕宽限期设成 0。
- 不登记打开文件的客户端（`wmfs fs`、测试里的参考客户端）不挡 gc：它们手上的旧布局随时可能被删，读到 `CHUNK_NOT_FOUND` 时按 C5
  重新取布局。
